🌉 Bắc cầu từ cái bạn đã biết

Bạn đã dùng Promise và biết một sự thật khó chịu: Promise không huỷ được. Gọi fetch() rồi đổi ý — request vẫn bay tới server, callback vẫn chạy. Muốn huỷ, bạn phải lôi AbortController vào và tự quản lý nó.

Bài này chỉ thêm một mảnh mới: Observable có sẵn nút tắt, và switchMap là thứ bấm nút đó giúp bạn.

1. Bài toán thật: ô tìm kiếm nói dối

Trang danh sách khoá học của EduCommerce có ô tìm kiếm gọi API mỗi khi người dùng gõ. Người dùng gõ "an", rồi gõ thêm thành "ang". Hai request bay đi. Mạng hôm đó phập phù nên chúng về ngược thứ tự:

Thời điểmViệc xảy raUI hiển thị
0msgõ "an" → request A bay đi—
150msgõ "ang" → request B bay đi—
400msrequest B về (kết quả của "ang")kết quả "ang" ✅
900msrequest A về (kết quả của "an")kết quả "an" ❌

Ô input đang hiện chữ "ang", nhưng danh sách bên dưới là kết quả của "an". Người dùng không hiểu chuyện gì. Bạn cũng không tái hiện được bug vì mạng công ty quá nhanh. Đây là race condition — và nó là bug kinh điển bậc nhất của mọi ô tìm kiếm trên đời.

🤔 Trước khi nhìn code

Thử nghĩ cách sửa bằng công cụ bạn đã biết. Rất nhiều người sửa bằng cách gắn số thứ tự cho request rồi bỏ qua response cũ. Nó chạy được. Nhưng nó vẫn để request A bay tới server và vẫn tốn băng thông, tốn quota API, và server vẫn chạy query nặng cho một từ khoá không ai cần nữa. Có cách nào chặn từ gốc không?

2. Mental model

Điều then chốt cần hiểu là: khi bạn viết source$.pipe(switchMap(x => api(x))), có hai tầng Observable chứ không phải một:

TầngLà ai ở ví dụ nàyVòng đời
Outer (nguồn) luồng từ khoá người dùng gõ sống suốt thời gian component còn tồn tại
Inner (được sinh ra) api("an"), api("ang")… — mỗi từ khoá đẻ ra một cái mới ngắn, và có thể bị giết giữa chừng

Toàn bộ họ operator switchMap / mergeMap / concatMap / exhaustMap làm cùng một việc: nhận giá trị từ outer, đẻ ra một inner. Chúng chỉ khác nhau ở đúng một câu hỏi: "khi inner cũ chưa xong mà outer đã bắn giá trị mới thì xử sao?"

💡 Hãy giữ câu này trong đầu

switch trong switchMap nghĩa là "chuyển kênh": bật kênh mới thì kênh cũ tắt hẳn, không phát song song.

Và "tắt hẳn" ở đây không phải cách nói ẩn dụ. Nó gọi unsubscribe() lên inner cũ, chạy hàm dọn dẹp của inner đó — với HttpClient thì hàm dọn dẹp gọi thẳng xhr.abort(), tức là request bị huỷ ở tầng mạng. Đây chính là thứ Promise không làm được nếu không có AbortController.

3. Nhìn mental model bằng code

Vấn đề của việc học RxJS qua console.log là bạn chỉ thấy kết quả, không thấy việc huỷ. Nên ta sẽ dựng một API giả có ghi nhật ký lúc bị huỷ. Chìa khoá nằm ở hàm teardown — thứ bạn return ra từ constructor của Observable:

TypeScript · src/playground/search-api.ts 
import { Observable } from 'rxjs';

/** Nhật ký dùng chung để test quan sát được API nào chạy, API nào bị huỷ. */
export type ApiLog = string[];

/**
 * API tìm kiếm GIẢ LẬP.
 * Điểm mấu chốt: hàm teardown (phần `return () => {...}`) chạy khi có người
 * unsubscribe — nhờ vậy ta CHỨNG MINH được request đã bị huỷ, thay vì chỉ tin.
 */
export function fakeSearchApi(term: string, delayMs: number, log: ApiLog): Observable<string[]> {
  return new Observable<string[]>((subscriber) => {
    // Chạy khi CÓ NGƯỜI subscribe — không phải khi hàm được gọi.
    // Đây là tính "lazy" của Observable: không ai nghe thì không có gì xảy ra.
    log.push(`START ${term}`);
    let xong = false;

    const id = setTimeout(() => {
      xong = true;
      subscriber.next([`${term} result`]);
      subscriber.complete();
    }, delayMs);

    // TEARDOWN: chạy khi unsubscribe HOẶC khi complete.
    // Cờ `xong` để phân biệt hai trường hợp — chỉ ghi CANCEL khi bị cắt giữa chừng.
    return () => {
      clearTimeout(id);
      if (!xong) log.push(`CANCEL ${term}`);
    };
  });
}
🔎 Điều cần quan sát

Hàm teardown chạy ở cả hai trường hợp: bị huỷ giữa chừng, và hoàn thành bình thường. Rất nhiều người tưởng nó chỉ chạy khi unsubscribe. Cờ xong tồn tại chính là để tách bạch hai trường hợp đó — và bản thân chi tiết nhỏ này là một câu phỏng vấn.

4. Pipeline hoàn chỉnh và vai trò từng mắt xích

TypeScript · pipeline search-as-you-type 
tuKhoa$
  .pipe(
    // (1) Chờ người dùng NGỪNG gõ 300ms rồi mới tính.
    //     Chặn loại rác: gõ 8 ký tự → 8 request.
    debounceTime(300),

    // (2) Bỏ qua nếu từ khoá y hệt lần trước.
    //     Chặn loại rác: gõ "ang" rồi xoá "x" thừa → vẫn "ang" → không gọi lại.
    distinctUntilChanged(),

    // (3) Đẻ inner Observable, và GIẾT inner trước đó nếu nó chưa xong.
    //     Chặn loại rác: response cũ về muộn ghi đè kết quả mới.
    switchMap((term) => fakeSearchApi(term, 500, log)),
  )
  .subscribe((r) => ketQua.push(r));

Ba operator này hay bị gộp chung thành "combo search" và học vẹt. Nhưng chúng chặn ba loại rác khác nhau, và bỏ cái nào cũng để lại một lỗ:

Bỏ điHậu quả cụ thể
không có debounceTime Gõ "angular" = 7 request. Server ăn đủ 7. Bill API nhân 7.
không có distinctUntilChanged Người dùng gõ rồi xoá về đúng chữ cũ → gọi lại API cho một từ khoá vừa gọi xong.
không có switchMap (dùng mergeMap) Race condition ở mục 1 — UI hiện kết quả của từ khoá đã xoá.
⚖️ Thứ tự có quan trọng không?

Có. debounceTime phải đứng trước switchMap. Đảo lại thành switchMap rồi debounceTime thì API đã bị gọi rồi mới đi debounce cái kết quả — tức là bạn debounce nhầm thứ, và mọi phím gõ vẫn thành một request.

5. Experiment nhỏ — nhìn tận mắt việc huỷ

🔮 Dự đoán trước khi chạy

Với pipeline ở mục 4 (debounce 300ms, API mất 500ms), kịch bản: gõ "an" → đợi 400ms → gõ "ang" → đợi 800ms.

Nhật ký log sẽ chứa những dòng nào, theo thứ tự nào? Viết ra giấy trước khi đọc tiếp.

Ta dùng đồng hồ giả của Vitest (vi.useFakeTimers()) để tua thời gian tức thì — test chạy trong vài mili-giây thay vì phải chờ thật, và kết quả tất định, không flaky.

TypeScript · trích từ src/playground/search-stream.spec.ts 
vi.useFakeTimers();

tuKhoa$.next('an');
vi.advanceTimersByTime(300);   // debounce nhả → API "an" BẮT ĐẦU (cần 500ms)
vi.advanceTimersByTime(100);   // API "an" mới chạy được 100/500ms

tuKhoa$.next('ang');
vi.advanceTimersByTime(300);   // debounce nhả → switchMap GIẾT "an" (mới 400/500) → API "ang" bắt đầu
vi.advanceTimersByTime(500);   // API "ang" xong

// Kết quả đã verify chạy XANH trên rxjs 7.8.2 / Vitest 4.1.10:
expect(log).toEqual(['START an', 'CANCEL an', 'START ang']);
expect(ketQua).toEqual([['ang result']]);

Kết quả cần quan sát: dòng 'CANCEL an' xuất hiện ngay trước 'START ang'. Đó là bằng chứng vật lý: switchMap không "bỏ qua kết quả cũ", nó ngắt kết nối tới nguồn cũ. Và ketQua chỉ có một phần tử — kết quả của "an" chưa từng chạm tới subscribe.

💡 Vì sao học RxJS tách khỏi Angular trước?

Vì nếu học chung, bạn sẽ không phân biệt được lỗi do RxJS hay do Angular change detection. Tách ra, feedback loop chỉ còn chưa tới 1 giây và mỗi lần đỏ bạn biết chắc vấn đề nằm ở luồng dữ liệu. Đây cũng là câu trả lời cho Câu hỏi tư duy ở Bài 00: RxJS lo luồng bất đồng bộ và vòng đời của nó; Angular chỉ đóng góp HttpClient (tạo Observable từ XHR) và async pipe (subscribe hộ rồi render).

7. Happy path chưa đủ

🔥 Production scenario: API trả lỗi 500

Người dùng gõ một từ khoá làm server sập. Inner Observable phát error. Câu hỏi: sau đó người dùng gõ tiếp từ khoá khác — ô tìm kiếm còn hoạt động không?

Không. Và đây là cái bẫy khiến rất nhiều ô tìm kiếm "chết im lặng" trên production. Lý do nằm ở hợp đồng cơ bản của Observable: error là một trạng thái kết thúc. Lỗi từ inner nổi lên outer, giết luôn cả subscription gốc. Từ đó về sau tuKhoa$.next(...) vẫn chạy nhưng không còn ai nghe.

Cách chữa là catchError đặt bên trong switchMap, để lỗi được nuốt ở tầng inner và không bao giờ chạm tới outer:

TypeScript · đặt catchError ĐÚNG chỗ 
// ❌ SAI: lỗi đã leo lên outer rồi mới bắt → stream chết luôn sau lần lỗi đầu.
switchMap((term) => searchApi(term)),
catchError(() => of([])),

// ✅ ĐÚNG: lỗi bị nuốt NGAY TRONG inner, outer không hề hay biết → stream sống tiếp.
switchMap((term) =>
  searchApi(term).pipe(
    catchError(() => of([])),   // lỗi → trả mảng rỗng, coi như "không tìm thấy"
  ),
),
🎤 Góc phỏng vấn

Hỏi: "Đặt catchError trong hay ngoài switchMap thì khác gì nhau?"

Trả lời gọn: "Ngoài thì bắt được lỗi nhưng stream chết vĩnh viễn, vì error là trạng thái kết thúc của Observable — nó đã giết outer subscription trước khi catchError kịp thay thế. Trong thì lỗi được xử lý ở phạm vi một request, outer vẫn sống và ô tìm kiếm dùng tiếp được. Với search box thì gần như luôn phải đặt bên trong."

8. Đối chiếu tài liệu chính thức

JSDoc gốc của switchMap trong source RxJS 7.x mô tả: "Projects each source value to an Observable which is merged in the output Observable, emitting values only from the most recently projected Observable" — và nói rõ: "When a new inner Observable is emitted, switchMap stops emitting items from the earlier-emitted inner Observable and begins emitting items from the new one."

Còn phần "huỷ tới tận tầng mạng" thì docs Angular về HttpClient nói thẳng: "Unsubscribing will abort the in-progress request. This is very useful if the Observable is subscribed via the async pipe, as it will automatically cancel the request if the user navigates away from the current page." Ghép hai mảnh lại: switchMap unsubscribe inner cũ → Angular abort XHR đó. Không có phép màu nào ở giữa.

🧩 Hint ladder — chỉ mở khi thật sự bí

Hint 1 · Hướng suy nghĩ:
Với đồng hồ giả, "chờ" không phải await — nó là vi.advanceTimersByTime(ms), chạy đồng bộ tức thì. Nghĩa là cả test của bạn không cần async.

Hint 2 · API cần dùng:
new Subject<string>() làm nguồn từ khoá · vi.useFakeTimers() mở đầu mỗi test · vi.advanceTimersByTime(ms) tua · expect(log).toEqual([...]) để so khớp chính xác cả thứ tự (đừng dùng toContain — nó không bắt được thứ tự sai).

Hint 3 · Khung sườn:
const log: ApiLog = [] → const tuKhoa$ = new Subject<string>() → tuKhoa$.pipe(debounceTime(300), distinctUntilChanged(), switchMap(t => fakeSearchApi(t, 500, log))).subscribe(r => ketQua.push(r)) → bắn giá trị xen kẽ với advanceTimersByTime → assert.

✅ Senior takeaway
  • Tôi giải thích được switchMap giải quyết vấn đề gì: race condition, không phải "gọi API gọn hơn".
  • Tôi hiểu vì sao nó huỷ được: teardown của Observable → xhr.abort().
  • Tôi biết khi nào không nên dùng nó: thao tác ghi/submit — chỗ đó dùng exhaustMap.
  • Tôi biết catchError phải nằm trong switchMap, và giải thích được vì sao.
  • Tôi đã chứng minh tất cả bằng test chạy được, không phải bằng niềm tin.

10. Câu hỏi tư duy

Trong mọi test của bài này, ta gọi .subscribe(...) mà không bao giờ gọi .unsubscribe(). Test vẫn xanh, không sao cả.

Nhưng khi pipeline này nằm trong CourseListComponent và người dùng rời trang giữa lúc request đang bay: tuKhoa$ là một Subject sống trong component, còn subscription thì đang giữ tham chiếu tới component đó. Ai giải phóng ai? Và chuyện gì xảy ra nếu response về sau khi component đã bị huỷ?
