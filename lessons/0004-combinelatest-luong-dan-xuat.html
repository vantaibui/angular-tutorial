🌉 Bắc cầu từ cái bạn đã biết

Bài 01 bạn có một nguồn (từ khoá) → một API. Bài 03 bạn biết BehaviorSubject luôn có sẵn giá trị hiện tại.

1. Bài toán thật: ba cái núm, một API

Trang danh sách khoá học có ba thứ người dùng đổi được — ô tìm kiếm, dropdown danh mục, số trang — và đúng một API nhận cả ba tham số. Cách làm ngây thơ:

TypeScript · ❌ cách làm sẽ khiến bạn hối hận 
// Ba biến rời + ba subscribe. Mỗi cái tự gọi lại API.
this.search$.subscribe((s) => { this.search = s; this.goiApi(); });
this.category$.subscribe((c) => { this.category = c; this.goiApi(); });
this.page$.subscribe((p) => { this.page = p; this.goiApi(); });

goiApi() {
  this.http.get(`/api/courses?search=${this.search}&category=${this.category}&page=${this.page}`)
    .subscribe((r) => (this.courses = r));   // ← subscribe LỒNG TRONG subscribe
}

Nó chạy. Rồi nó gây ra bốn vấn đề, tất cả đều xuất hiện muộn:

Vấn đềBiểu hiện thực tế
State rời rạc3 biến + 3 subject phải tự giữ đồng bộ. Thêm filter thứ tư = sửa 4 chỗ.
Không huỷ đượcsubscribe lồng nhau → request cũ không bị huỷ → race condition y hệt Bài 01.
Leak3 subscription phải tự dọn; subscribe bên trong lại càng khó dọn.
Không test đượcLogic nằm rải trong callback, không có một stream nào để assert.
🤔 Trước khi nhìn code

Điều bạn thực sự muốn diễn đạt là: "bộ filter hiện tại" là một giá trị duy nhất, được dẫn xuất từ ba nguồn. Nếu có một Observable đại diện cho chính nó, mọi vấn đề trên biến mất. Câu hỏi là ghép thế nào.

2. Mental model

combineLatest giữ một ô nhớ cho mỗi nguồn. Nguồn nào phát thì ghi đè ô của nó, rồi phát ra một mảng gồm nội dung tất cả các ô.

Hình dung — ba ô nhớ 
search$  ──"ang"──────────"angular"────────────────►
cat$     ────────"web"───────────────────"mobile"──►
page$    ──1────────────────────────────────────────►

           ô nhớ:  [search, cat, page]
                    ↓
phát ra:   ✗   ✗   ["ang","web",1]  ["angular","web",1]  ["angular","mobile",1]
           ▲   ▲
           └───┴─ IM LẶNG: chưa đủ cả ba ô
💡 Hãy giữ câu này trong đầu

combineLatest không phát gì cho tới khi mọi nguồn đã phát ít nhất một lần. Sau đó, nó phát lại mỗi khi bất kỳ nguồn nào đổi.

Hai vế của câu đó tạo ra hai cái bẫy riêng biệt — mục 3 và mục 5.

3. Bẫy số 1: trang trắng vĩnh viễn

🔮 Dự đoán trước khi chạy

search$ và cat$ là Subject thường. Người dùng gõ tìm kiếm hai lần nhưng chưa đụng vào dropdown danh mục. Có bao nhiêu lần API được gọi?

TypeScript · kết quả đã verify (rxjs 7.8.2) 
const search$ = new Subject<string>();
const cat$ = new Subject<string>();

combineLatest([search$, cat$]).subscribe(([s, c]) => r.push(`${s}|${c}`));

search$.next('ang');
expect(r).toEqual([]);              // ← IM LẶNG
search$.next('angular');
expect(r).toEqual([]);              // ← VẪN IM LẶNG
cat$.next('web');
expect(r).toEqual(['angular|web']);  // ← giờ mới nhả, lấy MỚI NHẤT của mỗi ô
🔥 Vì sao bug này tốn hàng giờ debug

Trang trắng, không lỗi console, Network tab trống trơn. Bạn đi tìm bug ở service, ở interceptor, ở MSW handler — trong khi API chưa từng được gọi lần nào. Nguyên nhân chỉ là một dropdown mà người dùng chưa đụng vào.

Cách chẩn đoán trong 10 giây: thấy combineLatest mà không thấy gì xảy ra → hỏi ngay "nguồn nào chưa từng phát?". Gắn tạm .pipe(tap(v => console.log('nguồn X', v))) lên từng nguồn, cái nào im là thủ phạm.

Hai cách chữa

TypeScript · cách 1 — startWith 
combineLatest([
  search$.pipe(startWith('')),        // mặc định: không tìm gì
  cat$.pipe(startWith('all')),        // mặc định: mọi danh mục
]).subscribe(...);
// → phát NGAY ['', 'all'] mà không cần ai đụng vào gì.
TypeScript · cách 2 — dùng BehaviorSubject ngay từ đầu (khuyến nghị) 
const search$ = new BehaviorSubject<string>('');
const cat$ = new BehaviorSubject<string>('all');

combineLatest([search$, cat$]).subscribe(...);
// → phát ngay, vì BehaviorSubject theo định nghĩa LUÔN có giá trị hiện tại (Bài 03).
💡 Chọn cách nào?

Cách 2, nếu bạn sở hữu nguồn. Vì filter là trạng thái chứ không phải sự kiện — đúng bảng chọn ở Bài 03. Dùng startWith khi nguồn không do bạn tạo (vd fromEvent, hoặc Observable từ thư viện ngoài).

4. Đưa nó vào EduCommerce

TypeScript · course-list.component.ts (xem trước Bài 28) 
// Mỗi núm điều khiển là một BehaviorSubject — luôn có giá trị hiện tại.
private readonly search$ = new BehaviorSubject<string>('');
private readonly category$ = new BehaviorSubject<string>('all');
private readonly page$ = new BehaviorSubject<number>(1);

// MỘT nguồn sự thật cho "bộ filter hiện tại".
// Dạng object (không phải mảng) để đọc dễ và không lệ thuộc thứ tự.
private readonly filter$ = combineLatest({
  search: this.search$.pipe(debounceTime(300)),  // chỉ gõ phím mới cần debounce
  category: this.category$,
  page: this.page$,
});

readonly courses$ = this.filter$.pipe(
  // Bỏ qua nếu bộ filter y hệt lần trước (xem bẫy số 2 ở mục 5).
  distinctUntilChanged((a, b) => JSON.stringify(a) === JSON.stringify(b)),

  // switchMap: filter mới → huỷ request cũ. Đúng bài học Bài 01.
  switchMap((f) => this.courseService.search(f).pipe(
    catchError(() => of({ data: [], meta: { page: 1, total: 0 } })),  // lỗi ở INNER (Bài 01)
  )),
);
// Template: <div *ngIf="courses$ | async as kq"> → async pipe tự unsubscribe (Bài 02).
💡 Nhìn lại: bốn bài đầu ghép thành một đoạn code

switchMap huỷ request cũ (Bài 01) · | async tự dọn subscription (Bài 02) · BehaviorSubject vì filter là trạng thái (Bài 03) · combineLatest gộp nguồn (Bài 04). Không dòng nào là "cú pháp cho đẹp" — mỗi dòng chặn một bug cụ thể.

💡 Dạng object dễ đọc hơn dạng mảng

combineLatest({ search, category, page }) trả về {search, category, page} thay vì [s, c, p]. Thêm filter thứ tư không làm hỏng thứ tự destructuring ở mọi nơi khác. Với 3 nguồn trở lên, gần như luôn nên dùng dạng object.

5. Bẫy số 2: đổi một filter, bắn hai request

Vế thứ hai của mental model — "phát lại mỗi khi bất kỳ nguồn nào đổi" — cũng có giá. Tình huống rất thật: đổi từ khoá tìm kiếm thì phải reset trang về 1.

TypeScript · kết quả đã verify 
search$.next('b');   // ô search đổi → phát ['b', 1]
page$.next(1);     // ô page ghi lại giá trị CŨ → vẫn phát ['b', 1] LẦN NỮA

expect(goiApi).toEqual(['a-1', 'b-1', 'b-1']);  // ← 'b-1' bị gọi HAI lần

Hai request giống hệt nhau bay đi. Tốn quota, và tệ hơn: chúng có thể về ngược thứ tự. Ba cách xử lý, theo mức độ nên dùng:

CáchƯuNhược
distinctUntilChanged so sánh sâu Đơn giản, chặn mọi trường hợp trùng JSON.stringify nhạy với thứ tự key; tốn chút CPU
debounceTime(0) trước switchMap Gộp mọi thay đổi trong cùng một tick thành một Thêm một tick trễ; khó hiểu với người đọc code sau
Gộp state thành một BehaviorSubject object Đúng gốc vấn đề: một hành động = một lần next Mất khả năng subscribe riêng từng filter
⚖️ Đừng chọn switchMap để "khỏi lo trùng"

switchMap huỷ request đầu nên UI vẫn đúng. Nhưng request thứ nhất vẫn đã bay tới server trước khi bị abort. Với API tính tiền theo lượt gọi, hoặc endpoint chạy query nặng, "UI đúng" không có nghĩa là "không tốn kém". Chặn ở tầng stream vẫn tốt hơn.

6. Ba anh em dễ nhầm

OperatorKhi nào phátDùng cho
combineLatest Bất kỳ nguồn nào đổi (sau khi đủ cả) Filter, form state — "cái gì đổi cũng phải tính lại"
withLatestFrom Chỉ nguồn chính đổi Submit form — "bấm nút mới chạy, nhưng cần dữ liệu form mới nhất"
zip Khi đủ một cặp theo chỉ số Ghép hai luồng song song 1-1. Hiếm dùng — dễ tắc nếu một bên chậm.
TypeScript · withLatestFrom — đã verify 
submit$.pipe(withLatestFrom(form$), map(([, f]) => f)).subscribe(...);

form$.next('v2');   // gõ form → KHÔNG kích hoạt gì (đúng ý muốn!)
submit$.next();      // bấm submit → nhận 'v2', giá trị mới nhất của form
🎤 Góc phỏng vấn

Hỏi: "combineLatest và withLatestFrom khác nhau chỗ nào?"

Trả lời gọn: "combineLatest đối xử mọi nguồn bình đẳng — bất kỳ nguồn nào đổi cũng phát. withLatestFrom có một nguồn chủ: chỉ nó kích hoạt, các nguồn kia chỉ đóng vai trò cung cấp giá trị mới nhất. Filter thì dùng combineLatest; submit form thì withLatestFrom, vì gõ form không được phép tự submit. Cả hai đều im lặng cho tới khi mọi nguồn đã phát ít nhất một lần."

🧩 Hint ladder — chỉ mở khi bị stuck

Hint 1 · Hướng suy nghĩ:
Toàn bộ bài này đồng bộ — không cần fake timer (trừ khi bạn thêm debounceTime). Assert ngay sau mỗi next() để thấy rõ thời điểm nào phát, thời điểm nào không. Đó mới là thứ bài này dạy.

Hint 2 · API cần dùng:
combineLatest([a$, b$]) hoặc combineLatest({a: a$, b: b$}) · startWith(v) · withLatestFrom(other$) · distinctUntilChanged((a, b) => ...).

Hint 3 · Mẹo cho TC5:
Điểm mấu chốt là page$.next(1) khi page$ đang là 1. BehaviorSubject không tự lọc giá trị trùng — nó vẫn phát. Ghi kết quả vào một mảng rồi khẳng định mảng đó có phần tử lặp lại liền nhau.

✅ Senior takeaway
  • Tôi biết combineLatest im lặng tới khi mọi nguồn phát — và chẩn đoán được bug đó qua Network tab trống.
  • Tôi biết nó phát lại khi bất kỳ nguồn nào đổi, và cách chặn request trùng.
  • Tôi chọn được giữa combineLatest / withLatestFrom / zip theo ngữ nghĩa.
  • Tôi không viết subscribe lồng nhau nữa — tôi gộp nguồn rồi switchMap.
  • Tôi giải thích được vì sao dạng object tốt hơn dạng mảng khi có ≥3 nguồn.

8. Câu hỏi tư duy

Bạn vừa viết courseService.search(filter). Sắp tới sẽ cần userService, reviewService, enrollmentService… và cả bốn đều có getAll, getById, create, update, delete — logic y hệt nhau, chỉ khác endpoint và kiểu dữ liệu.

Copy-paste bốn lần thì sửa một bug phải sửa bốn chỗ. Nhưng viết một service dùng chung trả về any thì mất hết type-safety — courseService.getById('x') lẽ ra phải trả Course chứ không phải "thứ gì đó".
