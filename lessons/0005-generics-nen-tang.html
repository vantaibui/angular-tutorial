Generics nền — tham số hoá kiểu dữ liệu

<T> không phải "cách viết any cho sang". Nó là thứ giữ mối liên hệ giữa đầu vào và đầu ra mà any phá vỡ.

⏱ ~35 phút · 🎯 Bắt trình biên dịch chứng minh giúp bạn · 🏷️ EduCommerce · nền cho GenericApiService

🎯 Sau bài này bạn phải làm được
  • Giải thích được vì sao any làm mất kiểu còn <T> thì không.
  • Viết generic function / interface, và biết khi nào TS tự suy ra kiểu, khi nào phải ghi tường minh.
  • Dùng constraint T extends {...} và nói được nó mở khoá điều gì.
  • Dùng keyof để hàm chỉ nhận đúng tên field có thật.
  • Chứng minh type-safety bằng @ts-expect-error — biến trình biên dịch thành bộ test.
🌉 Bắc cầu từ cái bạn đã biết

Bạn đã dùng generic hàng ngày mà có thể không để ý: Array<string>, Promise<User>, Observable<Course[]>, http.get<Course>(...). Mỗi lần gõ <...> đó, bạn đang truyền một kiểu vào như truyền tham số.

Bài này chỉ thêm một mảnh mới: tự viết thứ nhận tham số kiểu, thay vì chỉ dùng thứ người khác viết.

1. Bài toán thật: cùng một hàm, bốn kiểu dữ liệu

EduCommerce cần lấy phần tử đầu tiên của một mảng — cho Course[], User[], Review[], Enrollment[]. Hai lựa chọn quen thuộc:

TypeScript · hai cách sai theo hai kiểu khác nhau 
// Cách 1 — copy 4 lần: type-safe nhưng sửa 1 bug phải sửa 4 chỗ.
function dauTienCourse(ds: Course[]): Course | undefined { return ds[0]; }
function dauTienUser(ds: User[]): User | undefined { return ds[0]; }
// ... và 2 hàm nữa y hệt

// Cách 2 — dùng any: viết 1 lần nhưng VỨT BỎ toàn bộ kiểu.
function dauTien_any(ds: any[]): any { return ds[0]; }
🔥 Cái giá thật của any

Đây không phải lý thuyết — đoạn dưới đã chạy thật và không có lỗi biên dịch nào:

TypeScript · lỗi chính tả lọt tới runtime 
const x = dauTien_any([course]);
x.tiitle;   // ← sai chính tả 'title'. TS IM LẶNG. Runtime: undefined.
x.gia();    // ← method không tồn tại. TS IM LẶNG. Runtime: CRASH.

const y = dauTien([course]);   // bản generic
y?.title;   // ✅ OK, và IDE gợi ý được
y?.tiitle;  // ❌ Lỗi biên dịch NGAY: 'tiitle' không tồn tại trên Course
🤔 Trước khi nhìn lời giải

Vấn đề với any không phải "kiểu bị lỏng". Vấn đề là nó cắt đứt sợi dây giữa tham số và giá trị trả về. Hàm biết đầu vào là Course[], nhưng đầu ra thì "quên" mất điều đó. Cần một cách nhớ lại.

2. Mental model

Generic là tham số, nhưng cho kiểu. Đúng nghĩa đen — đặt cạnh nhau là thấy:

Đối chiếu: tham số giá trị vs tham số kiểu 
// Tham số GIÁ TRỊ: (x) là chỗ trống, điền lúc GỌI HÀM
function nhanDoi(x: number) { return x * 2; }
nhanDoi(5);              // x = 5

// Tham số KIỂU: <T> là chỗ trống, điền lúc GỌI HÀM (thường TS tự điền hộ)
function dauTien<T>(ds: T[]): T | undefined { return ds[0]; }
dauTien<Course>([c]);   // T = Course
dauTien([c]);           // T = Course (TS tự SUY RA từ đối số)
💡 Hãy giữ câu này trong đầu

any nói "tôi không quan tâm kiểu gì". <T> nói "tôi chưa biết kiểu gì, nhưng đầu ra sẽ đúng bằng đầu vào".

Chữ đúng bằng là toàn bộ giá trị của Generics. Nó giữ được quan hệ giữa các vị trí trong chữ ký hàm — thứ any xoá sạch.

💡 T chỉ là tên biến

Không có gì thiêng liêng ở chữ T. Quy ước: T (Type), K (Key), V (Value), E (Element), R (Return). Với generic phức tạp, hãy đặt tên có nghĩa: <TEntity, TKhoaChinh> đọc dễ hơn <T, K> rất nhiều.

3. Generic interface — khuôn cho mọi response API

Đây là generic bạn sẽ dùng nhiều nhất trong khoá. Mọi API của EduCommerce trả về cùng một hình dạng, chỉ khác phần data:

TypeScript · ApiResponse<T> 
// Một khuôn, mọi entity. Phần "vỏ" (meta) cố định, phần "ruột" (data) tham số hoá.
interface ApiResponse<T> {
  data: T;
  meta: { page: number; total: number };
}

// T = Course[] → data là mảng Course
const rc: ApiResponse<Course[]> = { data: [c], meta: { page: 1, total: 1 } };
rc.data[0].price;   // ✅ TS biết đây là number

// T = User → data là một User đơn lẻ
const ru: ApiResponse<User> = { data: u, meta: { page: 1, total: 1 } };
ru.data.email;      // ✅ TS biết đây là string

// @ts-expect-error data phải là User, không phải string
const sai: ApiResponse<User> = { data: 'x', meta: { page: 1, total: 1 } };
🔎 Đối chiếu với dự án của bạn

Mở mock-data/types.ts — file bạn đã có sẵn — và tìm ApiListResponse<T> ở gần cuối. Nó đã được viết theo đúng pattern này rồi. Bài 10 sẽ dùng chính nó làm kiểu trả về cho GenericApiService<T>.

4. Constraint — extends mở khoá cái gì

Đây là phần quan trọng nhất bài, và là tiêu chí ✅ của Lesson 0.2 trong lộ trình của bạn.

T không ràng buộc nghĩa là "bất kỳ kiểu nào". Mà nếu có thể là bất kỳ kiểu nào, TypeScript không cho phép bạn giả định gì về nó:

TypeScript · vì sao cần constraint 
// ❌ KHÔNG biên dịch được
function layId<T>(item: T): string {
  return item.id;
  //        ^^ Lỗi: Property 'id' does not exist on type 'T'.
  // TS nói đúng: T có thể là number, string, boolean... làm gì có .id
}

// ✅ Ràng buộc: "T là gì cũng được, MIỄN LÀ nó có id: string"
function layId<T extends { id: string }>(item: T): string {
  return item.id;   // ✅ Giờ TS chắc chắn .id tồn tại
}

layId(course);   // ✅ Course có id
layId(user);     // ✅ User có id

// @ts-expect-error {name: string} không có 'id' → vi phạm ràng buộc
layId({ name: 'không có id' });
💡 Câu trả lời cho tiêu chí ✅ của lộ trình

Hỏi: Khác nhau giữa T và T extends {id: string}? Vì sao ràng buộc đó cần thiết để gọi được item.id?

Đáp: T trần nghĩa là "bất kỳ kiểu nào", nên bên trong hàm/class, TypeScript chỉ cho phép làm những thao tác đúng với mọi kiểu — mà truy cập .id thì không đúng với number hay string, nên bị chặn. T extends {id: string} thu hẹp tập kiểu hợp lệ xuống "những kiểu có id: string", và đổi lại TypeScript cho phép bạn dùng .id bên trong. Ràng buộc là một cuộc trao đổi: bạn hẹp bớt đầu vào để đổi lấy quyền làm nhiều hơn ở bên trong.

⚖️ Đừng ràng buộc chặt hơn mức cần

Nếu hàm chỉ cần .id, hãy ràng buộc đúng { id: string } — đừng viết T extends Course. Ràng buộc chặt hơn mức cần biến một hàm dùng chung thành hàm dùng riêng, và bạn mất luôn lý do viết generic. Ràng buộc vừa đủ để làm được việc, không hơn.

5. keyof — chỉ nhận tên field có thật

keyof T là hợp của mọi tên field của T. Với Course, keyof Course là 'id' | 'title' | 'price' | ... — một union các chuỗi.

TypeScript · layTruong với keyof 
// K bị ràng buộc phải là MỘT TRONG các key của T.
// Kiểu trả về T[K] = kiểu của đúng field đó — không phải union của mọi field.
function layTruong<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const t: string = layTruong(course, 'title');  // ✅ TS biết là string
const p: number = layTruong(course, 'price');  // ✅ TS biết là number

// @ts-expect-error 'khong_co' không phải key của Course
layTruong(course, 'khong_co');
🔎 Điều tinh tế: vì sao cần hai tham số kiểu

Nếu viết layTruong<T>(obj: T, key: keyof T): T[keyof T] thì vẫn chặn được key sai, nhưng kiểu trả về là string | number | boolean | ... — union của mọi field. Bạn lại phải ép kiểu ở chỗ dùng.

Tách riêng K khiến TypeScript "ghim" đúng key bạn truyền vào và trả về đúng T[K]. Đây là lý do generic thường có nhiều tham số kiểu: mỗi cái giữ một mối liên hệ riêng. Bài 22 (Dynamic Form) sẽ dùng lại đúng kỹ thuật này để field.name chỉ nhận tên field có thật của model.

6. Default type param

TypeScript · giá trị mặc định cho tham số kiểu 
// B mặc định giống A — như tham số hàm có giá trị mặc định.
interface Cap<A, B = A> { trai: A; phai: B; }

const cungKieu: Cap<number> = { trai: 1, phai: 2 };            // B = number
const khacKieu: Cap<string, number> = { trai: 'a', phai: 2 };  // B = number

// @ts-expect-error phai mặc định cùng kiểu với trai (number)
const sai: Cap<number> = { trai: 1, phai: 'x' };

Bạn sẽ gặp lại nó ngay ở Bài 10: GenericApiService<T, TId = string> — hầu hết entity dùng id kiểu string, nhưng nếu có cái dùng number thì vẫn đổi được mà không phải sửa chỗ nào khác.

7. Biến trình biên dịch thành bộ test

Với generic, phần lớn giá trị nằm ở tầng kiểu — thứ biến mất hoàn toàn lúc runtime. Test thường không chạm tới được. Nhưng có một chỉ thị làm đúng việc đó:

TypeScript · @ts-expect-error 
// Ý nghĩa: "dòng NGAY DƯỚI phải có lỗi biên dịch".
// - Có lỗi  → biên dịch PASS (lỗi bị nuốt, đúng như mong đợi)
// - KHÔNG lỗi → biên dịch FAIL: "Unused '@ts-expect-error' directive"

// @ts-expect-error
layId({ name: 'không có id' });
💡 Vì sao nó mạnh hơn @ts-ignore

@ts-ignore chỉ tắt tiếng — nếu sau này lỗi biến mất, nó im lặng và bạn không biết ràng buộc đã hỏng. @ts-expect-error thì báo động khi lỗi biến mất. Nghĩa là nó thực sự là một assertion: nó bảo vệ ràng buộc kiểu của bạn khỏi bị vô hiệu hoá trong lần refactor tương lai.

Chạy kiểm tra bằng: npx tsc --noEmit -p tsconfig.spec.json. Im lặng = mọi ràng buộc kiểu bạn khẳng định đều đang có hiệu lực thật.

🧩 Hint ladder — chỉ mở khi bị stuck

Hint 1 · Hướng suy nghĩ:
Mỗi khi định gõ any, hãy hỏi: "kiểu này có liên quan tới kiểu nào khác trong chữ ký không?". Nếu có — đó là chỗ cần một tham số kiểu.

Hint 2 · Cú pháp:
Tham số kiểu đặt ngay sau tên, trước ngoặc đơn: function ten<T>(...). Ràng buộc dùng extends: <T extends { id: string }>. Nhiều tham số ngăn bằng dấu phẩy: <T, K extends keyof T>.

Hint 3 · Mẹo cho TC5:
Chỉ viết expect(layTruong(c,'title')).toBe('Angular') thì không chứng minh được gì về kiểu — runtime luôn đúng. Phải gán vào biến có kiểu tường minh: const t: string = layTruong(c, 'title'). Nếu kiểu trả về sai, dòng gán này sẽ đỏ.

✅ Senior takeaway
  • Tôi giải thích được Generics giữ quan hệ giữa các vị trí trong chữ ký, còn any xoá nó.
  • Tôi hiểu constraint là một cuộc trao đổi: hẹp đầu vào ↔ được làm nhiều hơn bên trong.
  • Tôi biết vì sao <T, K extends keyof T> cần hai tham số kiểu chứ không phải một.

9. Câu hỏi tư duy

Generic function nhận tham số kiểu ở mỗi lần gọi. Nhưng GenericApiService<Course> thì khác: kiểu được chốt một lần lúc tạo service, rồi mọi method bên trong — getAll, getById, update — đều phải nhớ và dùng chung kiểu đó.

Vậy tham số kiểu của một class sống ở đâu, và nó khác gì tham số kiểu của một function? Và nếu update chỉ muốn nhận vài field thay vì cả object, bạn diễn đạt điều đó bằng kiểu như thế nào?
