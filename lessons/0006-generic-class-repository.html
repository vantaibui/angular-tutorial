Generic class — InMemoryRepository<T>

Một class dùng chung cho mọi entity, mà mỗi chỗ dùng vẫn giữ nguyên kiểu riêng. Đây là bản thu nhỏ của GenericApiService<T> ở Bài 10.

⏱ ~35 phút · 🎯 Một class, hai entity, không một chữ any · 🏷️ EduCommerce · nền cho tầng service

🎯 Sau bài này bạn phải làm được
  • Viết generic class và biết tham số kiểu của class sống ở đâu.
  • Dùng Partial<T> cho method update — patch vài field vẫn type-safe.
  • Chứng minh repo Course từ chối nhận User.
  • Giải thích được điều gì không làm được nếu bỏ ràng buộc extends.
🌉 Bắc cầu từ cái bạn đã biết

Bài 05: tham số kiểu của function được điền ở mỗi lần gọi — dauTien([course]) thì T = Course chỉ trong lời gọi đó.

Bài này chỉ thêm một mảnh mới: tham số kiểu của class được chốt một lần lúc new, rồi mọi method bên trong dùng chung nó.

1. Bài toán thật: bốn service, một logic

Đây chính là câu hỏi tư duy cuối Bài 04. EduCommerce sẽ có CourseService, UserService, ReviewService, EnrollmentService — cả bốn đều cần getAll / getById / update / remove, logic giống hệt, chỉ khác kiểu dữ liệu.

Trước khi đụng vào HTTP (Bài 10), ta luyện đúng kỹ thuật đó trên một phiên bản không có gì để hỏng: kho lưu trong bộ nhớ.

🤔 Trước khi nhìn code

Tham số kiểu của function đặt sau tên hàm: function f<T>(...). Với class thì đặt ở đâu — để cả add, findById, update đều thấy được cùng một T?

2. Mental model

Đối chiếu — phạm vi sống của tham số kiểu 
// FUNCTION: T sinh ra và chết trong MỘT lời gọi.
function dauTien<T>(ds: T[]): T | undefined { ... }
dauTien([course]);  // T = Course, xong việc là hết
dauTien([user]);    // T = User, hoàn toàn độc lập với lời gọi trên

// CLASS: T chốt lúc `new`, sống suốt đời instance đó.
class Repo<T> {          // ← đặt ngay sau TÊN CLASS
  private items: T[] = [];   // mọi field...
  add(item: T) { ... }       // ...và mọi method đều thấy CÙNG một T
}

const repoCourse = new Repo<Course>();  // T = Course, VĨNH VIỄN cho instance này
const repoUser = new Repo<User>();      // instance khác, T khác, không liên quan
💡 Hãy giữ câu này trong đầu

Tham số kiểu của class là một lời hứa mà instance mang theo suốt đời: "tôi chỉ làm việc với đúng kiểu này".

3. Viết InMemoryRepository<T>

TypeScript · src/playground/repository.ts 
/** Ràng buộc `T extends { id: string }` là thứ cho phép class đụng vào item.id. */
export class InMemoryRepository<T extends { id: string }> {

  // private: không ai bên ngoài sửa mảng trực tiếp được.
  private items: T[] = [];

  add(item: T): void {
    this.items.push(item);
  }

  // Trả về `T | undefined` chứ KHÔNG phải `T`: tìm không thấy là chuyện bình thường,
  // và kiểu trả về phải nói ra sự thật đó để nơi gọi buộc phải xử lý.
  findById(id: string): T | undefined {
    return this.items.find((x) => x.id === id);   // ← .id dùng được NHỜ ràng buộc
  }

  // Partial<T> = mọi field của T thành optional.
  // Nhờ vậy patch 1 field vẫn hợp lệ, nhưng field LẠ thì vẫn bị chặn.
  update(id: string, patch: Partial<T>): void {
    const i = this.items.findIndex((x) => x.id === id);
    if (i === -1) return;                      // không thấy thì im lặng bỏ qua
    this.items[i] = { ...this.items[i], ...patch };  // tạo object MỚI, không sửa tại chỗ
  }

  remove(id: string): boolean {
    const i = this.items.findIndex((x) => x.id === id);
    if (i === -1) return false;
    this.items.splice(i, 1);
    return true;
  }

  // readonly T[]: người gọi đọc được nhưng không push/splice vào kho nội bộ.
  getAll(): readonly T[] {
    return this.items;
  }
}
🔎 Ba quyết định thiết kế đáng để ý

1. T | undefined thay vì T: kiểu trả về nên nói thật. Nếu khai là T, mọi nơi gọi sẽ tưởng luôn có kết quả và crash ở runtime. Khai | undefined thì TypeScript ép người gọi xử lý.

2. Tạo object mới trong update: {...cũ, ...patch} thay vì Object.assign(cũ, patch). Object mới ⇒ so sánh tham chiếu phát hiện được thay đổi — điều kiện sống còn cho OnPush change detection (Bài 40) và cho NgRx (Phase 9).

3. readonly T[]: chặn repo.getAll().push(...) ở tầng kiểu. Đóng cửa ghi bằng compiler, không bằng lời dặn trong code review.

4. Partial<T> — vừa lỏng vừa chặt đúng chỗ

Partial<T> là một utility type có sẵn: nó biến mọi field của T thành optional. Điều tinh tế là nó lỏng ở chiều "được phép bỏ qua" nhưng vẫn chặt ở chiều "tên field phải có thật":

TypeScript · đã verify bằng tsc 
repo.update('c1', { price: 80 });                  // ✅ patch 1 field
repo.update('c1', { price: 80, title: 'Mới' });     // ✅ patch nhiều field
repo.update('c1', {});                             // ✅ hợp lệ (không đổi gì)

// @ts-expect-error 'gia' không phải field của Course
repo.update('c1', { gia: 80 });

// @ts-expect-error price phải là number
repo.update('c1', { price: 'rẻ' });
Utility typeLàm gìDùng ở đâu trong khoá
Partial<T>Mọi field thành optionalupdate(), patch form
Required<T>Mọi field thành bắt buộcSau khi validate xong
Omit<T, K>Bỏ field Kcreate() — chưa có id
Pick<T, K>Chỉ giữ field KDTO gọn cho danh sách
Readonly<T>Mọi field chỉ đọcState trong NgRx
💡 Omit giải đúng một bài toán thật

Method create nhận entity chưa có id (server sẽ sinh). Chữ ký đúng là create(data: Omit<T, 'id'>): T — người gọi không được phép truyền id, và TypeScript ép đúng điều đó. Bài 10 sẽ dùng nó trong GenericApiService.

5. Chứng minh nó thực sự type-safe

TypeScript · một class, hai entity — đã verify 
const courses = new InMemoryRepository<Course>();
const users = new InMemoryRepository<User>();

courses.add({ id: 'c1', title: 'Angular', price: 100 });
users.add({ id: 'u1', name: 'Tài', role: 'admin' });

courses.findById('c1')?.price;   // ✅ TS biết là number
users.findById('u1')?.role;     // ✅ TS biết là 'student' | 'admin'

// @ts-expect-error repo Course KHÔNG nhận User
courses.add({ id: 'u2', name: 'x', role: 'student' });
🔎 So với bản dùng any

Một InMemoryRepository viết bằng any cũng chạy y hệt lúc runtime. Khác biệt duy nhất: bản any để bạn nhét User vào kho Course mà không kêu một tiếng, rồi crash ở một chỗ hoàn toàn khác, ba tuần sau. Generics không làm code chạy đúng hơn — nó làm code sai không biên dịch được.

6. Bỏ ràng buộc thì mất gì?

TypeScript · repo không ràng buộc 
class RepoKhongRangBuoc<T> {
  private items: T[] = [];
  add(i: T) { this.items.push(i); }
  count() { return this.items.length; }

  // KHÔNG viết được findById ở đây:
  // TS không biết T có .id hay không → `x.id` là lỗi biên dịch.
}

// Nó vẫn hữu ích — chỉ là hữu ích cho việc KHÁC:
const r = new RepoKhongRangBuoc<{ name: string }>();
r.add({ name: 'không có id' });   // ✅ nhận được kiểu KHÔNG có id
💡 Đánh đổi, không phải "cái nào tốt hơn"

Ràng buộc hẹp tập kiểu được phép, đổi lại mở những gì làm được bên trong. Không ràng buộc thì nhận được nhiều kiểu hơn nhưng làm được ít hơn.

Cách chọn: bắt đầu từ những gì class cần làm, rồi ràng buộc vừa đủ để làm được. Repo cần tra theo id ⇒ cần {id: string}, không hơn. Đừng viết T extends Course — nó biến generic thành không-generic.

🎤 Góc phỏng vấn

Hỏi: "Khi nào dùng generic class thay vì generic function?"

Trả lời gọn: "Khi có state cần giữ đúng kiểu qua nhiều lời gọi. Function generic chốt kiểu ở từng lời gọi, nên không nhớ được gì giữa các lần gọi. Class generic chốt kiểu lúc khởi tạo, nên mọi field và method dùng chung kiểu đó — như Repository<T> phải nhớ mảng nó đang giữ là mảng gì. Nếu chỉ biến đổi dữ liệu vào–ra mà không giữ state thì function là đủ và nhẹ hơn."

7. Xem trước: đây chính là GenericApiService

TypeScript · Bài 10 sẽ là repo này + HttpClient 
// Bài 06 (hôm nay) — kho trong bộ nhớ, đồng bộ:
findById(id: string): T | undefined {
  return this.items.find((x) => x.id === id);
}

// Bài 10 — cùng cấu trúc, đổi nguồn dữ liệu sang HTTP:
getById(id: string): Observable<T> {
  return this.http.get<T>(`${this.endpoint}/${id}`);
}
// Cùng một <T>, cùng một ràng buộc. Chỉ khác: đồng bộ → Observable.
// Và `http.get<T>` chính là một generic function do Angular viết sẵn (Bài 05).
⚖️ Generic không phải lúc nào cũng đáng

Nếu app chỉ có một entity, GenericApiService<T> là over-engineer thuần tuý: thêm một lớp trừu tượng để phục vụ đúng một trường hợp. Generic đáng giá khi bạn đã lặp lại ít nhất ba lần và thấy rõ khuôn chung. EduCommerce có 4–6 entity nên nó xứng đáng — nhưng hãy nhớ lý do, đừng generic vì thói quen.

🧩 Hint ladder — chỉ mở khi bị stuck

Hint 1 · Hướng suy nghĩ:
Bắt đầu từ chữ ký, chưa viết thân hàm. Mỗi method tự hỏi: "kiểu trả về có nói thật không?" — findById có thể không tìm thấy, nên phải | undefined.

Hint 2 · Cú pháp:
export class InMemoryRepository<T extends { id: string }> { ... } · Partial<T> · Omit<T, 'id'> · readonly T[] · merge bằng spread: { ...cu, ...patch }.

Hint 3 · Bẫy ở TC5:
Class không ràng buộc không được chứa findById — nếu bạn viết vào thì file sẽ không biên dịch. Đó chính là điều bài học muốn bạn tự đâm vào: hãy thử viết nó, đọc thông báo lỗi của TypeScript, rồi xoá đi và ghi lại lỗi đó thành comment.

✅ Senior takeaway
  • Tôi biết tham số kiểu class chốt lúc new và sống suốt đời instance.
  • Tôi dùng Partial/Omit/Pick để chữ ký nói đúng hợp đồng thật.
  • Tôi biết generic bị xoá lúc runtime — nên vẫn phải validate dữ liệu từ API.
  • Tôi ràng buộc vừa đủ để làm được việc, không chặt hơn.
  • Tôi biết khi nào generic là over-engineer và dám không dùng nó.
