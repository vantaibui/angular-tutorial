Phase 0 · Bài 07 · Core (Angular DI)

DI & injector tree — "gần nhất thắng"

Angular tìm service ở đâu, theo thứ tự nào — và vì sao providers đặt ở component lại tạo ra một instance riêng cho mỗi component.

⏱ ~40 phút · 🎯 Chứng minh injector tree bằng TestBed · 🏷️ Bài cuối Phase 0

🎯 Sau bài này bạn phải làm được
  • Nói đúng thứ tự resolve khi component xin một dependency.
  • Quyết định đặt providers ở đâu — root, module, hay component — và giải thích vì sao.
  • Dùng InjectionToken để inject thứ không phải class (config object).
  • Giải thích multi: true — cơ chế đứng sau HTTP_INTERCEPTORS ở Phase 4.
🌉 Bắc cầu từ cái bạn đã biết

Bài 06 bạn new InMemoryRepository<Course>() bằng tay — bạn kiểm soát hoàn toàn có bao nhiêu instance. Trong Angular bạn không gọi new; bạn khai báo nhu cầu và Angular đưa cho.

Bài này chỉ thêm một mảnh mới: Angular quyết định đưa cho bạn instance nào — theo một luật đơn giản: gần nhất thắng.

1. Bài toán thật: giỏ hàng dùng chung ngoài ý muốn

EduCommerce có CartService giữ giỏ hàng. Đúng như mong đợi: header, trang Cart, trang Checkout đều thấy cùng một giỏ. Hợp lý — đó là state toàn cục.

Giờ bạn làm tính năng "So sánh khoá học": mở ba panel cạnh nhau, mỗi panel có giỏ nháp riêng. Bạn tái sử dụng CartService và… cả ba panel chia sẻ chung một giỏ. Thêm vào panel 1 thì panel 2 và 3 cũng đổi theo.

🤔 Trước khi nhìn code

Cách sửa ngây thơ: tạo DraftCartService riêng rồi tự new trong component. Nhưng như thế bạn mất DI hoàn toàn — không mock được khi test, không inject được HttpClient vào trong đó.

Câu hỏi thật là: có cách nào giữ nguyên DI mà đổi số lượng instance không?

2. Mental model: hai cái cây, một luật

Angular duy trì hai hệ thống injector song song. Đây là chỗ hầu hết tài liệu giải thích mơ hồ, nên hãy nắm chắc:

CâyTạo ra từSố lượng
ElementInjector providers trong @Component / @Directive Một cho mỗi phần tử DOM có khai providers
EnvironmentInjector
(xưa gọi ModuleInjector)		 providers trong @NgModule, và providedIn Một cho root, thêm một cho mỗi module lazy-load
Thứ tự tìm kiếm khi component xin một dependency 
Component xin CartService
   │
   ├─ 1. ElementInjector của CHÍNH nó          ← providers: [CartService] ở đây?
   ├─ 2. ElementInjector của component CHA
   ├─ 3. ... đi ngược lên tới gốc cây DOM
   │
   ├─ 4. EnvironmentInjector của module        ← providers: [...] trong @NgModule?
   ├─ 5. ... đi ngược lên EnvironmentInjector gốc  ← providedIn: 'root' / @Service()
   │
   └─ 6. Không thấy → NullInjectorError
         (trừ khi có @Optional() → trả về null)

// LUẬT: dừng ở CÁI ĐẦU TIÊN tìm thấy. Không tìm tiếp.
💡 Hãy giữ câu này trong đầu

Angular đi từ chỗ bạn đứng ngược lên gốc, và lấy cái đầu tiên gặp được. Muốn đổi instance nào được đưa cho bạn — hãy đặt provider gần hơn.

Theo docs chính thức về hierarchical DI: Angular tìm trong ElementInjector và các cha của nó trước; nếu không thấy, "it goes back to the element where the request originated and looks in the EnvironmentInjector hierarchy"; và "the first one Angular encounters is the one it uses to resolve the dependency".

3. Ba chỗ đặt provider — và hệ quả của mỗi chỗ

TypeScript · ba mức, ba số lượng instance 
// ── MỨC 1: ROOT ── một instance cho TOÀN APP (singleton)
@Injectable({ providedIn: 'root' })
export class AuthService { }
// Dùng cho: auth, cart toàn cục, config, logger.
// Ưu điểm phụ: tree-shakable — không ai inject thì không vào bundle.


// ── MỨC 2: MODULE ── một instance cho phạm vi module đó
@NgModule({ providers: [CourseFilterService] })
export class CoursesModule { }
// Lưu ý quan trọng: với module EAGER (import thẳng vào AppModule),
// provider vẫn gộp vào injector GỐC → vẫn là singleton toàn app.
// Chỉ module LAZY-LOAD mới thực sự có EnvironmentInjector riêng.


// ── MỨC 3: COMPONENT ── một instance cho MỖI INSTANCE component
@Component({
  selector: 'app-compare-panel',
  standalone: false,
  providers: [DraftCartService],   // ← 3 panel = 3 giỏ nháp độc lập
})
export class ComparePanelComponent {
  draft = inject(DraftCartService);
}
🔥 Bẫy kinh điển: "provider ở module = scope riêng"

Rất nhiều người tin rằng đặt providers trong một feature module thì service đó chỉ sống trong module ấy. Sai với module eager. Angular gộp providers của mọi module eager vào một injector gốc duy nhất. Đặt UserService trong AdminModule (eager) thì trang public vẫn inject được nó bình thường.

Chỉ lazy-loaded module mới tạo EnvironmentInjector con thật sự. Bài 12 sẽ chạm lại đúng điểm này khi làm lazy-load — và đó cũng là lý do CoreModule cần cơ chế chống import hai lần (Bài 08).

4. Chứng minh bằng TestBed

Ba test dưới đây đã chạy xanh thật — chúng chứng minh trọn vẹn mental model ở mục 2:

TypeScript · providers ở COMPONENT → instance riêng 
@Component({ selector: 'app-con', template: '', standalone: false,
             providers: [GioHangService] })   // ← mỗi component một bản
class ConCoProviderComponent {
  gioHang = inject(GioHangService);
}

// --- test ---
const f1 = TestBed.createComponent(ConCoProviderComponent);
const f2 = TestBed.createComponent(ConCoProviderComponent);

f1.componentInstance.gioHang.them('khoa-hoc-1');

expect(f1.componentInstance.gioHang.soLuong()).toBe(1);
expect(f2.componentInstance.gioHang.soLuong()).toBe(0);   // ← KHÔNG dùng chung
expect(f1.componentInstance.gioHang).not.toBe(f2.componentInstance.gioHang);
TypeScript · KHÔNG khai providers → đi ngược lên, dùng chung 
@Component({ selector: 'app-khong', template: '', standalone: false })  // không providers
class ConKhongProviderComponent {
  gioHang = inject(GioHangService);
}

TestBed.configureTestingModule({ imports: [DemoModule], providers: [GioHangService] });

f1.componentInstance.gioHang.them('x');
expect(f2.componentInstance.gioHang.soLuong()).toBe(1);   // ← DÙNG CHUNG
expect(f1.componentInstance.gioHang).toBe(f2.componentInstance.gioHang);
🔎 Test thứ ba mới là cái chốt lại luật

Khai provider ở cả hai nơi — module và component — rồi so sánh: component nhận bản của chính nó, không phải bản của module. Đó chính là "gần nhất thắng", và nó cũng là cách bạn ghi đè một service cho riêng một nhánh cây component mà không đụng tới phần còn lại của app.

5. InjectionToken — inject thứ không phải class

DI của Angular dùng khoá để tra provider. Với class, chính class đó là khoá. Nhưng interface AppConfig thì biến mất khi biên dịch — không còn gì để làm khoá. Đó là lý do InjectionToken tồn tại:

TypeScript · core/tokens/app-config.token.ts 
export interface AppConfig { apiUrl: string; pageSize: number; }

// Một object THẬT tồn tại lúc runtime, mang theo kiểu ở tầng type.
// Chuỗi 'app.config' chỉ để hiển thị trong thông báo lỗi — không phải định danh.
export const APP_CONFIG = new InjectionToken<AppConfig>('app.config');

// Đăng ký
@NgModule({
  providers: [
    { provide: APP_CONFIG, useValue: { apiUrl: '/api', pageSize: 20 } },
  ],
})
export class CoreModule {}

// Dùng — type-safe hoàn toàn, IDE gợi ý được .pageSize
export class CourseService {
  private config = inject(APP_CONFIG);
}

Bốn kiểu provider

TypeScript · useValue / useClass / useFactory / useExisting 
// useValue — giá trị có sẵn. Dùng cho config, hằng số, mock trong test.
{ provide: APP_CONFIG, useValue: { apiUrl: '/api', pageSize: 20 } }

// useClass — tráo implementation. Chỗ dùng KHÔNG đổi một dòng nào.
{ provide: GioHangService, useClass: GioHangGia }
// → TestBed.inject(GioHangService) trả về instance của GioHangGia.
// Đây chính là cách mock service khi test (Bài 45).

// useFactory — cần TÍNH TOÁN, hoặc phụ thuộc dependency khác.
{
  provide: 'BASE_URL',
  useFactory: (c: AppConfig) => `${c.apiUrl}/courses`,
  deps: [APP_CONFIG],   // ← BẮT BUỘC liệt kê, Angular không tự suy ra được
}

// useExisting — bí danh: hai khoá trỏ về CÙNG một instance.
{ provide: LoggerInterface, useExisting: ConsoleLogger }

6. multi: true — nhiều provider, một mảng

Bình thường provider sau ghi đè provider trước cho cùng một khoá. Với multi: true thì chúng cộng dồn thành mảng:

TypeScript · đã verify 
const VALIDATOR = new InjectionToken<string[]>('validators');

TestBed.configureTestingModule({
  providers: [
    { provide: VALIDATOR, useValue: 'required', multi: true },
    { provide: VALIDATOR, useValue: 'maxLength', multi: true },
  ],
});

expect(TestBed.inject(VALIDATOR)).toEqual(['required', 'maxLength']);
🔎 Vì sao bạn cần biết điều này ngay bây giờ

Đây chính xác là cơ chế đứng sau HTTP_INTERCEPTORS ở Bài 24:

TypeScript · xem trước Bài 24 
providers: [
  { provide: HTTP_INTERCEPTORS, useClass: AuthInterceptor, multi: true },
  { provide: HTTP_INTERCEPTORS, useClass: LoggingInterceptor, multi: true },
]
// Angular gom thành mảng rồi chạy chúng theo ĐÚNG THỨ TỰ khai báo.
// QUÊN `multi: true` → interceptor sau GHI ĐÈ cái trước, và bạn mất một cái
// mà KHÔNG có lỗi nào cả. Bug im lặng kinh điển của Angular Classic.

7. Angular 22 có @Service() — thứ codebase cũ của bạn chưa có

⚖️ Đây là điểm lệch giữa sân tập và codebase v12–v16

Tôi đã kiểm trực tiếp trong @angular/core@22.1.2 đang cài trên máy bạn: decorator @Service() có thật, và @Injectable không bị đánh dấu deprecated. Cả hai chạy song song.

TypeScript · đối chiếu — đã verify chạy xanh 
// ── Cách CỔ ĐIỂN (mọi codebase v12–v16 dùng cái này) ──
@Injectable({ providedIn: 'root' })
class AuthService { }

@Injectable()                    // phải tự khai trong providers
class GioHangService { }

// ── Cách MỚI của Angular 22 ──
@Service()                       // tự động provided ≈ providedIn:'root'
class ThongBaoService { }

@Service({ autoProvided: false })  // ≈ @Injectable() trần
class GioHangService2 { }

Theo JSDoc trong chính file type của Angular 22: "When autoProvided is set to false, the service won't be exposed to the dependency injection system automatically. It is up to the user to expose it in a providers list."

🔥 Khoá này dùng @Injectable, có chủ đích

Mission của bạn là đọc hiểu và maintain codebase Angular cũ. Những codebase đó không có @Service(). Học @Injectable trước là đúng thứ tự. Nhưng giờ bạn biết @Service() tồn tại — nếu người phỏng vấn hỏi "Angular mới nhất có gì thay đổi về DI", bạn trả lời được, và trả lời chính xác thay vì theo tin đồn trên blog.

8. 🎯 Your turn

🛠 Task — src/playground/di.spec.ts

Bài này chấm bằng pnpm test. Bạn sẽ cần TestBed — lần đầu tiên trong khoá bạn chạm vào công cụ test của Angular.

Tiêu chí (Definition of Done)
  • TC1 — providedIn: 'root': hai lần TestBed.inject() trả về cùng một object (dùng toBe, không phải toEqual).
  • TC2 — providers ở component: tạo hai instance component, đổi state ở cái thứ nhất, khẳng định cái thứ hai không bị ảnh hưởng.
  • TC3 — Không khai ở component, khai ở module: hai instance component dùng chung một service.
  • TC4 — "Gần nhất thắng": khai ở cả hai nơi, khẳng định instance của component khác instance lấy từ module.
  • TC5 — InjectionToken + useValue: inject được một config object và đọc đúng field.
  • TC6 — multi: true: hai provider cùng token → nhận về mảng hai phần tử đúng thứ tự khai báo.

Thử thách thêm: TC7 — useClass tráo một implementation giả và chứng minh TestBed.inject(ServiceThat) trả về bản giả. Đây chính là kỹ thuật mock bạn sẽ dùng suốt Phase 10.

🧩 Hint ladder — chỉ mở khi bị stuck

Hint 1 · Hướng suy nghĩ:
Câu hỏi cốt lõi luôn là "cùng một object hay hai object khác nhau?". Nên dùng toBe (so sánh tham chiếu) chứ không dùng toEqual (so sánh nội dung) — hai instance rỗng khác nhau vẫn toEqual nhau, và test của bạn sẽ xanh một cách vô nghĩa.

Hint 2 · API cần dùng:
TestBed.configureTestingModule({ imports: [...], providers: [...] }) · TestBed.inject(Token) · TestBed.createComponent(Comp) → .componentInstance · new InjectionToken<T>('mo-ta') · inject(X) làm field initializer trong component.

Hint 3 · Bẫy setup:
Component dùng trong test phải có standalone: false và phải được declarations trong một @NgModule, rồi imports module đó vào TestBed. Nhớ gọi lại configureTestingModule ở mỗi test — cấu hình không tự reset giữa các test khi bạn đổi providers.

✅ Senior takeaway — và hết Phase 0
  • Tôi đọc thuộc thứ tự resolve: ElementInjector → cha → EnvironmentInjector → lỗi.
  • Tôi biết "gần nhất thắng" và dùng nó để ghi đè service cho một nhánh component.
  • Tôi biết provider ở module eager vẫn là singleton toàn app — không phải scope riêng.
  • Tôi dùng InjectionToken cho mọi thứ không phải class, và biết 4 kiểu provider.
  • Tôi hiểu multi: true và hậu quả im lặng khi quên nó.
  • Tôi biết Angular 22 có @Service(), nhưng chọn @Injectable vì mission là codebase cũ.
