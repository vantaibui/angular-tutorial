🌉 Bắc cầu từ cái bạn đã biết

Bài 10 bạn có lớp abstract với constructor protected nhận HttpClient và endpoint. Bài 07 bạn dùng inject() làm field initializer.

Bài này chỉ thêm một mảnh mới: inject() gọi được ngay bên trong super().

1. Bài toán thật: boilerplate của lớp con

TypeScript · cách viết truyền thống 
@Injectable({ providedIn: 'root' })
export class CourseService extends GenericApiService<Course> {
  // Dòng này KHÔNG mang thông tin gì riêng của Course —
  // nhưng phải lặp lại y hệt ở CẢ SÁU service.
  constructor(http: HttpClient) {
    super(http, '/api/courses');
  }
}

Nó chạy được. Nhưng http: HttpClient là nhiễu: nó không nói gì về CourseService, chỉ là ống dẫn để đưa dependency xuống lớp cha. Sáu entity là sáu lần lặp.

🤔 Trước khi nhìn lời giải

Thứ duy nhất phân biệt CourseService với UserService là chuỗi endpoint và tham số kiểu. Lý tưởng nhất, đó phải là hai thứ duy nhất bạn phải gõ.

2. Mental model: inject() chạy ở đâu

inject() không phải phép màu — nó đọc một injector "đang hoạt động" mà Angular đặt sẵn trong lúc dựng instance. Angular gọi nó là injection context.

Vị tríinject() dùng được?
Field initializer (private x = inject(Y))✅
Thân constructor✅
Bên trong super(...)✅ — vẫn trong lúc dựng instance
ngOnInit, event handler, callback❌ NG0203
💡 Hãy giữ câu này trong đầu

inject() dùng được ở bất cứ đâu trong lúc Angular đang dựng instance — và super() nằm trong khoảng thời gian đó.

3. Viết hai service

TypeScript · src/app/core/services/course.service.ts 
import { HttpClient } from '@angular/common/http';
import { Injectable, inject } from '@angular/core';
import { GenericApiService } from './generic-api.service';
import { Course } from '../models/types';

@Injectable({ providedIn: 'root' })
export class CourseService extends GenericApiService<Course> {
  constructor() {
    // inject() gọi được NGAY TRONG super() — vẫn đang trong injection context.
    // Nhờ vậy lớp con không phải khai lại HttpClient làm tham số.
    super(inject(HttpClient), '/api/courses');
  }

  // Method RIÊNG của Course — lớp cơ sở không biết tới.
  // Đây là lý do dùng KẾ THỪA thay vì chỉ gọi hàm dùng chung:
  // chỗ để đặt thứ đặc thù mà vẫn giữ nguyên CRUD.
  getBestsellers() {
    return this.getAll({ bestseller: 'true' });
  }
}
TypeScript · src/app/core/services/user.service.ts 
@Injectable({ providedIn: 'root' })
export class UserService extends GenericApiService<User> {
  constructor() {
    super(inject(HttpClient), '/api/users');
  }
}

UserService chỉ có 5 dòng mà đã có đủ getAll / getById / create / update / remove, tất cả gõ đúng kiểu User.

⚖️ providedIn: 'root' ở lớp CON, không phải lớp cha

Lớp cha abstract không đăng ký gì vào DI (Bài 10). Mỗi lớp con là một service riêng biệt với endpoint riêng, nên mỗi cái tự khai providedIn: 'root'. Kết quả: CourseService và UserService là hai singleton độc lập.

4. Chứng minh nó thật sự type-safe

TypeScript · trích từ spec đã verify 
it('getById trả về ĐÚNG kiểu Course, không phải any', async () => {
  const p = firstValueFrom(courseService.getById('c1'));
  const req = httpMock.expectOne('/api/courses/c1');
  req.flush(fakeCourse);

  const kq = await p;
  // Gán vào biến khai TƯỜNG MINH là cách duy nhất chứng minh kiểu.
  // Nếu getById trả `any`, dòng này vẫn qua — nên phải kèm @ts-expect-error bên dưới.
  const gia: number = kq.price;
  expect(gia).toBe(100);
});

it('type-safe: service Course không nhận User', () => {
  // @ts-expect-error create của CourseService không nhận User
  // .subscribe() BẮT BUỘC: Observable lazy, không subscribe thì không có request (Bài 03).
  courseService.create(u).subscribe();
  httpMock.expectOne('/api/courses').flush({});
});
🔎 Vì sao @ts-expect-error mới là bằng chứng thật

Test runtime không chứng minh được type-safety — nếu getById trả any, mọi assertion runtime vẫn xanh y hệt. Chỉ @ts-expect-error + tsc mới bắt được: nó đỏ khi lỗi kiểu biến mất (Bài 05).

5. Khi nào KHÔNG nên kế thừa

🔥 Kế thừa là quan hệ chặt nhất trong OOP

Sửa lớp cơ sở là ảnh hưởng cả sáu service cùng lúc. Với CRUD thuần thì đáng — vì chúng thật sự giống nhau. Nhưng khi một entity bắt đầu lệch (vd Review tạo qua POST /api/courses/:id/reviews chứ không phải /api/reviews), đừng cố nhồi vào lớp cha bằng cờ điều kiện.

Tình huốngNên làm
Entity khớp hoàn toàn CRUD chuẩnKế thừa — như UserService
Khớp CRUD + có thêm method riêngKế thừa rồi thêm method — như getBestsellers
Vài endpoint lệch hẳnoverride đúng method đó
Lệch quá nửaĐừng kế thừa — viết service riêng, hoặc compose: giữ một GenericApiService làm field thay vì extends
🎤 Góc phỏng vấn

Hỏi: "Khi nào chọn composition thay vì inheritance cho tầng service?"

Trả lời gọn: "Kế thừa khi lớp con thật sự là một biến thể của lớp cha và dùng gần như toàn bộ hành vi — CRUD theo REST chuẩn là ví dụ tốt. Composition khi chỉ cần một phần, hoặc khi lớp con phải chống lại hành vi mặc định. Dấu hiệu chọn sai: bắt đầu override method chỉ để ném lỗi 'không hỗ trợ', hoặc thêm cờ boolean vào lớp cha để phân nhánh cho một lớp con."

🧩 Hint ladder — chỉ mở khi bị stuck

Hint 1 · Hướng suy nghĩ:
Lớp con chỉ nên chứa thứ riêng của nó: tham số kiểu, endpoint, và method đặc thù. Thấy mình gõ thứ gì lặp lại ở cả hai service — đó là dấu hiệu nó thuộc về lớp cha.

Hint 2 · API cần dùng:
inject(HttpClient) từ @angular/core · @Injectable({providedIn:'root'}) trên lớp con · override keyword khi ghi đè method của cha.

Hint 3 · Nếu TypeScript than về super():
Kiểm constructor lớp cha là protected (không phải private), và lớp con không khai field nào trước super() — JavaScript bắt buộc super() phải là lệnh đầu tiên.
