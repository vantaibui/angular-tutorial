Bài này chỉ thêm một mảnh mới: tham số route mang theo cấu hình mà file routing gửi cho guard.

1. Bài toán thật: guard nổ theo tổ hợp

EduCommerce có 3 vai trò (student, instructor, admin). Viết guard riêng cho từng tổ hợp:

TypeScript · ❌ hướng đi sai 
AdminGuard · InstructorGuard · StudentGuard
AdminOrInstructorGuard · InstructorOrStudentGuard · ...

Ba vai trò đã là 7 tổ hợp. Thêm vai trò moderator là 15. Và mỗi guard chỉ khác nhau đúng một mảng chuỗi.

🤔 Trước khi nhìn lời giải

Thứ thay đổi là dữ liệu (danh sách vai trò), không phải logic (kiểm tra vai trò có nằm trong danh sách không). Nên đáng lẽ chỉ cần một guard nhận dữ liệu từ ngoài. Nhưng canActivate không có tham số nào để bạn truyền vào — vậy truyền bằng đường nào?

2. Mental model: data là kênh cấu hình tĩnh của route

TypeScript · route gửi cấu hình cho guard 
{
  path: 'dashboard',
  canActivate: [AuthGuard, RoleGuard],
  // data: object TĨNH gắn vào route, guard/component/resolver đều đọc được.
  data: { roles: ['admin', 'instructor'] },
  loadChildren: ...,
}
💡 Hãy giữ câu này trong đầu

Guard là logic dùng chung. route.data là cấu hình riêng của từng route. Tách hai thứ ra thì một guard phục vụ được vô hạn tổ hợp.

Đây chính là pattern bạn đã gặp ở Bài 07 với InjectionToken + useValue: tách hành vi khỏi tham số. Chỉ khác là ở đây kênh truyền là route chứ không phải DI.

3. Viết RoleGuard

TypeScript · src/app/core/guards/role.guard.ts 
@Injectable({ providedIn: 'root' })
export class RoleGuard implements CanActivate {
  private readonly auth = inject(AuthService);
  private readonly router = inject(Router);

  canActivate(route: ActivatedRouteSnapshot, state: RouterStateSnapshot): boolean | UrlTree {
    const user = this.auth.currentUser;

    // Chưa đăng nhập -> /login kèm returnUrl. KHÔNG phải /forbidden.
    // Phòng khi RoleGuard bị dùng một mình mà không có AuthGuard đứng trước.
    if (!user) {
      return this.router.createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });
    }

    // route.data là Record<string, any> -> phải ép kiểu, và LUÔN phòng thủ khi thiếu.
    // Quên khai data.roles mà crash guard là hỏng cả app, nên mặc định là "cho qua".
    const allowed = (route.data['roles'] as UserRole[] | undefined) ?? [];
    if (allowed.length === 0 || allowed.includes(user.role)) return true;

    // Đã đăng nhập nhưng sai quyền -> 403, KHÔNG đá về /login.
    return this.router.createUrlTree(['/forbidden']);
  }
}
🔥 Đá người sai quyền về /login là bug UX kinh điển

Học viên bấm nhầm link Dashboard. Nếu bạn đá họ về /login, họ thấy form đăng nhập trong khi đang đăng nhập. Họ sẽ nhập lại mật khẩu, thành công, rồi bị đá về /login lần nữa — vòng lặp vô tận, và họ tưởng tài khoản bị lỗi.

Hai tình huống, hai ý nghĩa khác hẳn nhau:

Tình huốngTương đương HTTPĐi đâu
Chưa đăng nhập401 Unauthorized/login?returnUrl=... — "cho tôi biết bạn là ai"
Đã đăng nhập, sai quyền403 Forbidden/forbidden — "tôi biết bạn là ai, và bạn không được vào"

4. Thứ tự guard — và vì sao nó quan trọng

TypeScript 
canActivate: [AuthGuard, RoleGuard]   // chạy TUẦN TỰ, trái sang phải

Angular chạy lần lượt và dừng ngay khi có guard không trả true. Nên thứ tự quyết định người dùng thấy gì:

Thứ tựNgười chưa đăng nhập thấyĐúng chưa?
[AuthGuard, RoleGuard]/login?returnUrl=...✅ đúng
[RoleGuard, AuthGuard]tuỳ RoleGuard có tự kiểm đăng nhập không⚠️ mong manh

Đó là lý do RoleGuard ở mục 3 vẫn tự kiểm !user dù thường có AuthGuard đứng trước: guard nên đúng kể cả khi đứng một mình. Đừng để tính đúng đắn phụ thuộc vào thứ tự trong một mảng mà ai đó có thể sắp lại.

TypeScript · test chứng minh thứ tự — đã verify 
it('thứ tự guard: AuthGuard chạy TRƯỚC RoleGuard', async () => {
  // Chưa đăng nhập + sai role: nếu RoleGuard chạy trước sẽ ra /forbidden.
  // Ra /login chứng minh AuthGuard chặn trước.
  await router.navigate(['/dashboard']);
  expect(router.url).toContain('/login');
});

5. Happy path chưa đủ

⚖️ route.data KHÔNG được kiểm kiểu

data có kiểu Record<string, any>. Gõ nhầm data: { role: ['admin'] } (thiếu chữ s) thì không có lỗi biên dịch nào — guard đọc data['roles'] ra undefined, rơi vào nhánh mặc định, và cho qua tất cả.

Một lỗi chính tả biến route admin thành route công khai. Nên tôi để mặc định là "cho qua" có chủ đích — nhưng phải kèm test cho từng route quan trọng. Cách chặt hơn: định nghĩa một interface RouteData và một helper đọc data có kiểu, thay vì đọc chuỗi thô ở mọi guard.

🔥 Guard không phải bảo mật

Toàn bộ code này chạy trong browser của người dùng. Mở DevTools, đặt auth.currentUser = {role:'admin'} là vào được ngay.

Guard tồn tại để trải nghiệm đúng (không loé trang, không tải chunk thừa) và tránh gọi API vô ích. Server vẫn phải kiểm quyền trên mọi endpoint. Nếu API tin vào việc "client đã chặn rồi" thì bạn có một lỗ hổng thật.

7. Câu hỏi tư duy — bắc cầu sang Phase 3

Guard đã chặn được người lạ. Giờ tới trang /login — và nó cần một form: email, mật khẩu, hiển thị lỗi khi bỏ trống hay sai định dạng, nút submit chỉ bật khi hợp lệ.

Bạn có thể làm bằng [(ngModel)] và vài biến boolean. Nó chạy cho form hai ô. Nhưng form đăng ký cần xác nhận mật khẩu — một luật kiểm tra giữa hai ô với nhau, không thuộc về ô nào.

Luật đó nên sống ở đâu? Và nếu nó phải sống ở "ô cha", thì cấu trúc form của bạn phải trông như thế nào?
