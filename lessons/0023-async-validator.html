1. Bài toán thật: 17 ký tự, 17 request

Người dùng gõ nguyen@gmail.com. Validator ngây thơ gọi API mỗi lần giá trị đổi — 17 request, phần lớn cho email dở dang như ngu, nguye@.

Và chúng có thể về ngược thứ tự: kết quả của nguye tới sau kết quả của nguyen@gmail.com và ghi đè lên. Đúng race condition Bài 01, lần này nằm trong validator.

2. Mental model: ba trạng thái, không phải hai

PENDING làm form.valid là false — "chưa biết" được coi như "chưa hợp lệ".

Đây không phải chi tiết vụn: nó là thứ khiến [disabled]="form.invalid" tự động chặn người dùng submit trong lúc đang kiểm email. Nếu PENDING được tính là valid, người gõ nhanh sẽ bấm Submit trước khi server kịp trả lời — và đăng ký được email trùng.

3. Code

TypeScript · src/app/core/validators/email-exists.validator.ts 
export function emailExistsValidator(http: HttpClient, debounceMs = 400): AsyncValidatorFn {
  return (control: AbstractControl): Observable<ValidationErrors | null> => {
    const email = (control.value ?? '').trim();

    // Rỗng thì để Validators.required lo — đừng gọi API cho chuỗi rỗng.
    // of(null) hoàn thành NGAY nên control không kẹt PENDING.
    if (!email) return of(null);

    return timer(debounceMs).pipe(
      // switchMap: gõ tiếp -> Angular gọi lại validator -> lần kiểm trước bị HUỶ.
      switchMap(() =>
        http.get<{ exists: boolean }>('/api/users/check-email', { params: { email } }),
      ),
      map((res) => (res.exists ? { emailExists: true } : null)),
      // Lỗi mạng KHÔNG được làm form invalid vĩnh viễn -> coi như hợp lệ,
      // để server chặn lần cuối. Xem mục 5.
      catchError(() => of(null)),
    );
  };
}
TypeScript · gắn vào form — tham số THỨ BA 
form = this.fb.group({
  email: [
    '',
    [Validators.required, Validators.email],        // đồng bộ — chạy trước
    [emailExistsValidator(this.http)],              // BẤT ĐỒNG BỘ — vị trí thứ 3
  ],
});
🔥 Nhét async validator vào mảng thứ hai = im lặng không chạy

[..., [Validators.required, emailExistsValidator(http)]] — TypeScript không phải lúc nào cũng bắt được, và validator sẽ không bao giờ chạy. Không lỗi, không cảnh báo, form luôn báo hợp lệ. Nhớ: sync ở vị trí 2, async ở vị trí 3.

⚖️ Vì sao timer() chứ không debounceTime()

debounceTime chỉ có nghĩa trên một stream liên tục. Nhưng Angular gọi validator lại từ đầu mỗi lần giá trị đổi — mỗi lần là một Observable mới, nên debounceTime không có gì để gộp.

timer(400) tạo độ trễ, và Angular tự huỷ Observable của lần validate trước khi giá trị đổi. Kết quả giống debounce, nhưng đúng cơ chế.

5. Happy path chưa đủ

🔥 Lỗi mạng: chọn "cho qua" hay "chặn"?
TypeScript 
catchError(() => of(null))                       // A: coi như HỢP LỆ
catchError(() => of({ khongKiemTraDuoc: true }))   // B: coi như KHÔNG hợp lệ
A — cho quaB — chặn
Mất mạngVẫn đăng ký đượcKhông đăng ký được

Tôi chọn A vì đây là kiểm tra tiện lợi, không phải kiểm tra bảo mật — server vẫn phải kiểm email trùng khi tạo tài khoản (đúng tinh thần "guard là UX, không phải bảo mật" ở Bài 14). Chặn người dùng vì API của mình lỗi là trừng phạt sai người.

Với validator bảo mật thật (vd kiểm mã giảm giá còn hạn), chọn B — nhưng phải kèm thông báo rõ và nút thử lại.

⚖️ Async validator KHÔNG chạy lại khi submit

Người dùng gõ email, chờ kiểm xong (VALID), rồi ngồi 10 phút mới bấm Submit. Trong 10 phút đó ai đó đã đăng ký email này. Form vẫn báo VALID vì validator không chạy lại.

Đây là lý do không bao giờ được tin async validator thay cho kiểm tra ở server.

6. Test bằng fake timer

TypeScript · test đã verify 
it('email đã tồn tại -> lỗi emailExists', () => {
  vi.useFakeTimers();
  const c = new FormControl('a@b.com', { asyncValidators: [emailExistsValidator(http, 400)] });

  expect(c.status).toBe('PENDING');      // chưa hết debounce
  vi.advanceTimersByTime(400);          // tua qua timer

  const req = httpMock.expectOne((r) => r.url === '/api/users/check-email');
  expect(req.request.params.get('email')).toBe('a@b.com');
  req.flush({ exists: true });

  expect(c.errors?.['emailExists']).toBe(true);
  expect(c.status).toBe('INVALID');
});

it('lỗi mạng -> KHÔNG làm form invalid vĩnh viễn', () => {
  vi.useFakeTimers();
  const c = new FormControl('a@b.com', { asyncValidators: [emailExistsValidator(http, 400)] });
  vi.advanceTimersByTime(400);
  httpMock.expectOne((r) => r.url === '/api/users/check-email')
    .flush({ message: 'sap' }, { status: 500, statusText: 'Server Error' });

  expect(c.status).toBe('VALID');   // quyết định A ở mục 5
});

Đúng kỹ thuật Bài 01: fake timer để tua thời gian, và HttpTestingController (Bài 10) để không cần server. Test chạy trong mili-giây, tất định, không flaky.

8. Câu hỏi tư duy — bắc cầu sang Phase 4

Form đăng ký xong. Người dùng bấm Đăng nhập, server trả về một token. Từ giờ mọi request đều phải kèm Authorization: Bearer <token>.

Bạn có thể thêm header thủ công trong GenericApiService (Bài 10). Nhưng token còn hết hạn — và khi hết hạn, mọi request trả 401, phải gọi refresh rồi thử lại request cũ.

Có chỗ nào nằm giữa HttpClient và mạng để làm cả hai việc đó một lần cho tất cả request? Và nếu 5 request cùng nhận 401 một lúc, làm sao chỉ gọi refresh một lần thay vì 5 lần?
