Class HttpInterceptor + HTTP_INTERCEPTORS

Đính token vào mọi request mà không sửa một dòng nào ở nơi gọi — nơi multi: true (Bài 07) được dùng thật lần đầu tiên.

⏱ ~35 phút · 🎯 Mọi request tự có Authorization header · 🏷️ Mở màn Module 5

🎯 Sau bài này bạn phải làm được
  • Viết class implement HttpInterceptor, đăng ký qua HTTP_INTERCEPTORS.
  • Giải thích interceptor là một pipeline, không phải một điểm chặn đơn lẻ.
  • Biết thứ tự khai báo quyết định thứ tự chạy — và hậu quả khi đảo ngược.
  • Test interceptor bằng HttpTestingController, không cần server thật.
🌉 Bắc cầu từ cái bạn đã biết

Bài 07: multi: true gom nhiều provider cùng token thành một mảng, và tôi nói trước "đây chính là cơ chế của HTTP_INTERCEPTORS". Bài 10: GenericApiService<T> gọi this.http.get(...) — không hề biết gì về token hay header.

Bài này chỉ thêm một mảnh mới: một lớp đứng giữa mọi lời gọi HttpClient và mạng thật, có quyền đọc và sửa request/response đi qua.

1. Bài toán thật: 40 chỗ gọi API, 40 chỗ phải nhớ đính token

EduCommerce có hàng chục service (CourseService, UserService, CartService...). Sau khi đăng nhập, mọi request cần header Authorization: Bearer <token>. Cách ngây thơ:

TypeScript · ❌ nhớ đính token ở TỪNG service 
getAll() {
  const token = localStorage.getItem('token');
  return this.http.get('/api/courses', {
    headers: { Authorization: `Bearer ${token}` },
  });
}

Lặp lại ở 40 chỗ. Đổi cách lưu token (localStorage → cookie) là sửa 40 chỗ. Quên một chỗ — request đó âm thầm thiếu token, và bug chỉ lộ ra khi người dùng report "sao trang này lúc được lúc không".

🤔 Trước khi nhìn lời giải

GenericApiService không nên biết gì về token — đó không phải việc của nó. Cần một chỗ duy nhất, nằm ngoài mọi service, có thể thấy được mọi request đi qua. Angular có chừa sẵn chỗ đó chưa?

2. Mental model: pipeline, không phải một cái bẫy

Request đi qua chuỗi interceptor trước khi ra mạng 
Service gọi http.get('/api/courses')
        │
        ▼
  Interceptor 1 ──► next.handle(req) ──► Interceptor 2 ──► ... ──► Mạng thật
        ▲                                                              │
        └──────────────── response đi NGƯỢC LẠI qua từng interceptor ──┘

// Mỗi interceptor CÓ THỂ: đọc/sửa request trước khi next.handle(),
// và đọc/sửa response sau khi nó quay về (qua .pipe() trên kết quả next.handle()).
💡 Hãy giữ câu này trong đầu

Interceptor không "bắt" request — nó đứng trên đường đi của MỌI request, và tự quyết định có sửa gì hay không trước khi gọi next.handle() để request đi tiếp.

3. Viết interceptor

TypeScript · src/app/core/services/auth-interceptor.service.ts (rút gọn) 
@Injectable()   // KHÔNG providedIn:'root' — interceptor không tự đăng ký, phải khai tường minh (mục 4)
export class AuthInterceptor implements HttpInterceptor {
  private readonly auth = inject(AuthService);

  intercept(req: HttpRequest<unknown>, next: HttpHandler): Observable<HttpEvent<unknown>> {
    const token = this.auth.accessToken;
    const authReq = token ? this.addToken(req, token) : req;
    return next.handle(authReq);
  }

  private addToken(req: HttpRequest<unknown>, token: string): HttpRequest<unknown> {
    // HttpRequest BẤT BIẾN — không có req.headers.set(). Phải .clone() ra bản MỚI.
    return req.clone({ setHeaders: { Authorization: `Bearer ${token}` } });
  }
}
🔥 HttpRequest bất biến — req.headers.set() không tồn tại

Cùng triết lý bất biến với HttpParams (Bài 10) và mảng trong CVA (Bài 18). Muốn "sửa" request, bạn phải .clone() ra bản mới với phần thay đổi. Quên điều này và cố sửa tại chỗ sẽ không biên dịch được — TypeScript chặn ngay vì HttpRequest không có setter công khai.

4. Đăng ký — nơi multi: true của Bài 07 dùng thật

TypeScript · src/app/core/core.module.ts 
@NgModule({
  providers: [
    // Angular 22: HttpClientModule đã deprecated -> dùng provideHttpClient.
    // withInterceptorsFromDi() giữ cho class-based interceptor (HTTP_INTERCEPTORS) vẫn chạy.
    provideHttpClient(withInterceptorsFromDi()),
    // multi: true -> nhiều interceptor CỘNG DỒN thành mảng, không ghi đè nhau (Bài 07).
    { provide: HTTP_INTERCEPTORS, useClass: AuthInterceptor, multi: true },
  ],
})
export class CoreModule { ... }
🔥 Quên multi: true — bug im lặng bạn đã học từ Bài 07

Thiếu nó, interceptor thứ hai bạn thêm sau này sẽ ghi đè interceptor này, không lỗi không cảnh báo. Đây không phải nhắc lại lý thuyết suông — Module 5 là nơi đầu tiên bạn thực sự thấy hậu quả nếu quên.

5. Thứ tự chạy — đảo ngược thì hỏng gì

TypeScript · nhiều interceptor CHẠY THEO ĐÚNG THỨ TỰ KHAI BÁO 
providers: [
  { provide: HTTP_INTERCEPTORS, useClass: AuthInterceptor, multi: true },     // chạy TRƯỚC
  { provide: HTTP_INTERCEPTORS, useClass: LoggingInterceptor, multi: true },  // chạy SAU
]
// Request: Auth -> Logging -> mạng.  Response: mạng -> Logging -> Auth.
⚖️ Nếu LoggingInterceptor log Authorization header

Đảo thứ tự (Logging trước Auth) thì log sẽ thiếu token — vì Auth chưa kịp đính vào lúc Logging đọc request. Thứ tự không phải chi tiết trang trí; nó quyết định interceptor sau có "thấy" được thay đổi của interceptor trước hay không.

6. Test bằng HttpTestingController

TypeScript · test đã verify xanh 
it('đính Authorization header từ access token hiện có', async () => {
  localStorage.setItem('edu_access_token', 'abc123');

  const p = firstValueFrom(http.get('/api/x'));
  const req = httpMock.expectOne('/api/x');
  expect(req.request.headers.get('Authorization')).toBe('Bearer abc123');
  req.flush({});
  await p;
});

it('không có token thì KHÔNG có header Authorization', async () => {
  const p = firstValueFrom(http.get('/api/x'));
  const req = httpMock.expectOne('/api/x');
  expect(req.request.headers.has('Authorization')).toBe(false);
  req.flush({});
  await p;
});
🔎 Đăng ký interceptor trong TestBed y hệt core.module.ts

providers: [provideHttpClient(withInterceptorsFromDi()), provideHttpClientTesting(), { provide: HTTP_INTERCEPTORS, useClass: AuthInterceptor, multi: true }] — thiếu withInterceptorsFromDi() thì interceptor class âm thầm không chạy, và test sẽ sai mà không rõ vì sao.

🎤 Góc phỏng vấn

Hỏi: "Interceptor hoạt động như thế nào? Sao phải .clone()?"

Trả lời gọn: "Interceptor là một mắt xích trong pipeline mà mọi request đi qua trước khi ra mạng, và response đi ngược lại qua đúng các mắt xích đó. Nó đăng ký qua HTTP_INTERCEPTORS — một multi-provider, nên nhiều interceptor cộng dồn thành mảng chạy theo thứ tự khai báo. HttpRequest bất biến để đảm bảo interceptor sau không vô tình đọc phải state đã bị sửa nửa chừng — muốn đổi phải .clone() ra bản mới."

8. Câu hỏi tư duy

Token của bạn hết hạn sau 15 phút. Server trả 401 cho request dùng token hết hạn. Bạn có thể bắt lỗi này ở từng service rồi tự gọi refresh — nhưng đó lại quay về đúng vấn đề mục 1: lặp lại ở 40 chỗ.

Interceptor bạn vừa viết đã đứng đúng chỗ để thấy mọi response, kể cả lỗi 401. Nhưng có một cái bẫy nguy hiểm hơn nhiều: nếu 5 request cùng hết hạn cùng lúc (trang vừa mở, bắn 5 request song song), bạn sẽ gọi refresh 5 lần — và có thể nhận về 5 access token khác nhau, ghi đè lẫn nhau.
