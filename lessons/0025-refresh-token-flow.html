Refresh token — bài toán RxJS khó nhất của app

5 request cùng nhận 401, chỉ đúng một lần gọi refresh, cả 5 tự retry — dùng lại chính BehaviorSubject bạn học ở Bài 03, lần này làm "hàng đợi".

⏱ ~50 phút · 🎯 Chứng minh bằng test: 5 request → 1 refresh · 🏷️ Câu hỏi senior kinh điển

🎯 Sau bài này bạn phải làm được
  • Giải thích vì sao 5 request 401 song song có thể gây 5 lần gọi refresh nếu code ngây thơ.
  • Dùng BehaviorSubject<string|null> làm "cổng chờ" cho request đến sau.
  • Biết vì sao catchError phải đặt lồng trong nhánh refresh, không đặt ở ngoài.
  • Test được cả nhánh thành công lẫn thất bại của refresh, và trường hợp không kích hoạt vòng lặp.
🌉 Bắc cầu từ cái bạn đã biết

Bài 24: interceptor là pipeline, thấy mọi response kể cả lỗi. Bài 03: BehaviorSubject luôn có "giá trị hiện tại", người tới muộn nhận được ngay — và nếu giá trị là null, người tới muộn biết là "chưa có gì, phải chờ".

Bài này chỉ thêm một mảnh mới: dùng đúng tính chất "chờ rồi nhận" đó để biến 5 lời gọi refresh trùng lặp thành 1.

1. Bài toán thật: mở trang, bắn 5 request, 5 lần refresh

Trang Dashboard load xong gọi song song: getCourses(), getUsers(), getEnrollments(), getReviews(), getStats(). Access token vừa hết hạn — cả 5 đều nhận 401 gần như cùng lúc.

TypeScript · ❌ cách ngây thơ — mỗi 401 tự gọi refresh 
handle401(req, next) {
  return this.auth.refreshAccessToken().pipe(
    switchMap((newToken) => next.handle(addToken(req, newToken))),
  );
}

Nhìn hợp lý — nhưng cả 5 request đều đi qua đúng dòng này độc lập, không biết về nhau. Kết quả: 5 request refresh bay lên server. Nếu server tự thu hồi refresh token cũ sau mỗi lần dùng (bảo mật tốt), 4 trong 5 lần refresh sẽ thất bại vì refresh token đã bị request đầu tiên "dùng hết" — người dùng bị đăng xuất giữa chừng dù đang dùng app bình thường.

🤔 Trước khi nhìn lời giải

4 request tới sau không cần tự refresh — chúng chỉ cần biết khi nào có token mới rồi dùng lại. Có cấu trúc nào phát ra đúng một giá trị cho nhiều người đang chờ cùng lúc?

2. Mental model: cờ chặn + cổng chờ

Hai biến, hai vai trò khác nhau 
private isRefreshing = false;
// Cờ: "có ai đang refresh KHÔNG?" — chặn không cho gọi refresh() lần hai.

private refreshTokenSubject = new BehaviorSubject<string | null>(null);
// Cổng chờ: null = "chưa xong". Request tới sau LẮNG NGHE cổng này,
// tự retry khi cổng phát ra token khác null. Đây chính là Bài 03 áp dụng ngược lại:
// "người tới MUỘN nhận được giá trị mới" — nhưng ở đây ta CỐ Ý coi null là 'chưa sẵn sàng'.
💡 Hãy giữ câu này trong đầu

Request đầu tiên 401 thì TỰ LÀM (gọi refresh). Mọi request 401 SAU ĐÓ, trong lúc đang refresh, chỉ ĐỨNG CHỜ ở cổng — không tự làm gì cả.

3. Code đầy đủ

TypeScript · src/app/core/services/auth-interceptor.service.ts 
@Injectable()
export class AuthInterceptor implements HttpInterceptor {
  private readonly auth = inject(AuthService);
  private readonly router = inject(Router);

  private isRefreshing = false;
  private readonly refreshTokenSubject = new BehaviorSubject<string | null>(null);

  intercept(req: HttpRequest<unknown>, next: HttpHandler): Observable<HttpEvent<unknown>> {
    const token = this.auth.accessToken;
    const authReq = token ? this.addToken(req, token) : req;

    return next.handle(authReq).pipe(
      catchError((error: HttpErrorResponse) => {
        // Đừng bắt 401 của CHÍNH endpoint login/refresh -> tránh vòng lặp vô hạn.
        if (error.status === 401 && !req.url.includes('/api/auth/')) {
          return this.handle401(req, next);
        }
        return throwError(() => error);
      }),
    );
  }

  private handle401(req: HttpRequest<unknown>, next: HttpHandler): Observable<HttpEvent<unknown>> {
    if (!this.isRefreshing) {
      // ── NGƯỜI ĐẦU TIÊN: tự làm việc ──
      this.isRefreshing = true;
      this.refreshTokenSubject.next(null); // báo: "đang refresh, ai tới sau thì chờ"

      return this.auth.refreshAccessToken().pipe(
        switchMap((newToken) => {
          this.isRefreshing = false;
          this.auth.setAccessToken(newToken);
          this.refreshTokenSubject.next(newToken); // đánh thức MỌI người đang chờ
          return next.handle(this.addToken(req, newToken));
        }),
        catchError((err) => {
          this.isRefreshing = false;
          this.auth.logout();
          this.router.navigate(['/login']);
          return throwError(() => err);
        }),
      );
    }

    // ── NGƯỜI TỚI SAU: đứng chờ ở cổng, không tự refresh ──
    return this.refreshTokenSubject.pipe(
      filter((t): t is string => t !== null),  // bỏ qua giá trị null (đang chờ)
      take(1),                                // lấy đúng 1 lần rồi TỰ HUỶ -> không leak (Bài 02)
      switchMap((newToken) => next.handle(this.addToken(req, newToken))),
    );
  }
}
🔎 Vì sao take(1) ở đây quan trọng như ở Bài 02

Không có take(1), mỗi request-chờ sẽ subscribe vĩnh viễn vào refreshTokenSubject — lần refresh tiếp theo (sau này, khi token lại hết hạn) sẽ vô tình kích hoạt lại logic switchMap của những request đã xong từ lâu. take(1) đảm bảo subscription tự đóng ngay sau khi nhận đúng một giá trị.

4. Chứng minh bằng test — 5 request, 1 refresh

TypeScript · test đã verify xanh 
it('5 request cùng 401 -> CHỈ 1 lần refresh, cả 5 retry thành công', async () => {
  localStorage.setItem('edu_access_token', 'token-cu-het-han');
  localStorage.setItem('edu_refresh_token', 'refresh-hop-le');

  const results$ = forkJoin([
    http.get('/api/a'), http.get('/api/b'), http.get('/api/c'), http.get('/api/d'), http.get('/api/e'),
  ]);
  const p = firstValueFrom(results$);

  // Cả 5 request gốc đều bay ra và đều nhận 401
  for (const url of ['/api/a', '/api/b', '/api/c', '/api/d', '/api/e']) {
    httpMock.expectOne(url).flush({ message: 'expired' }, { status: 401, statusText: 'Unauthorized' });
  }

  // MẤU CHỐT: dù 5 request cùng 401, chỉ ĐÚNG MỘT request refresh được gửi.
  const refreshReq = httpMock.expectOne('/api/auth/refresh');
  refreshReq.flush({ accessToken: 'token-moi' });

  for (const url of ['/api/a', '/api/b', '/api/c', '/api/d', '/api/e']) {
    const retried = httpMock.expectOne(url);
    expect(retried.request.headers.get('Authorization')).toBe('Bearer token-moi');
    retried.flush({ url });
  }

  expect(await p).toHaveLength(5);
  httpMock.verify();  // KHÔNG còn request nào chưa xử lý -> không có refresh thừa
});
🔎 Vì sao httpMock.expectOne('/api/auth/refresh') là trái tim của test

expectOne ném lỗi nếu có nhiều hơn một request khớp URL đó. Nếu logic của bạn vô tình gọi refresh 5 lần, dòng này sẽ đỏ ngay — test tự nó là bằng chứng, không cần đếm request bằng mắt.

5. Happy path chưa đủ

🔥 catchError đặt SAI CHỖ — bẫy giống hệt Bài 01
TypeScript 
// ❌ SAI: catchError ở NGOÀI toàn bộ pipe của intercept()
intercept(req, next) {
  return next.handle(req).pipe(
    switchMap(...), // xử lý 401
  );
}
catchError(() => ...)  // đặt rời, không thuộc pipe nào cả -> vô nghĩa/lỗi cú pháp thật

// ✅ ĐÚNG (như code mục 3): catchError bọc next.handle() ở TẦNG NGOÀI CÙNG,
// và catchError THỨ HAI nằm bên trong nhánh refresh để bắt lỗi refresh thất bại.

Đây là bài học Bài 01 (đặt catchError trong hay ngoài switchMap) quay lại ở quy mô lớn hơn: interceptor có hai tầng lỗi cần bắt riêng — lỗi của request gốc (401) và lỗi của chính việc refresh (refresh token cũng hết hạn). Trộn chung một catchError sẽ không phân biệt được hai tình huống cần xử lý khác nhau.

🔥 Bug thật tôi gặp khi soạn bài này

Test "refresh thất bại" gọi this.router.navigate(['/login']). Nếu router test không có route 'login' nào, Angular ném NG04002: Cannot match any routes — một unhandled rejection âm thầm làm ô nhiễm cả lượt chạy test, dù các expect() vẫn xanh. Bài học: khi test có nhánh gọi router.navigate(), route đích phải tồn tại thật trong provideRouter([...]) của test, dù chỉ là component rỗng.

🎤 Góc phỏng vấn

Hỏi: "Làm sao tránh gọi refresh token nhiều lần khi nhiều request cùng 401?"

Trả lời gọn: "Dùng một cờ isRefreshing để chỉ request đầu tiên thực sự gọi refresh, và một BehaviorSubject<string|null> làm cổng chờ — request tới sau lọc bỏ giá trị null bằng filter, lấy đúng một lần bằng take(1), rồi tự retry với token mới khi cổng phát ra. Quan trọng không kém: loại trừ chính endpoint /api/auth/* khỏi logic bắt 401, nếu không sẽ có vòng lặp vô hạn khi refresh cũng trả 401."

🧩 Hint ladder

Hint 1: Vẽ lại sơ đồ mục 2 ra giấy trước khi viết code. Xác định rõ: điều kiện nào để vào nhánh "tự làm", điều kiện nào để vào nhánh "chờ".

Hint 2 · API: BehaviorSubject<string|null> · filter((t): t is string => t !== null) · take(1) · switchMap · forkJoin để bắn nhiều request song song trong test.

Hint 3: Nếu TC2 báo "found more than one matching request", in log thứ tự request thật ra để xem có phải nhánh "tự làm" bị vào nhiều lần không — thường là do đặt isRefreshing = true sau bước bất đồng bộ thay vì ngay lập tức.

✅ Senior takeaway
  • Tôi giải quyết được race condition kinh điển: N request 401 → 1 refresh, không phải N.
  • Tôi dùng đúng vai trò của cờ boolean (chặn) và BehaviorSubject (cổng chờ) — không lẫn lộn hai việc.
  • Tôi loại trừ endpoint auth khỏi vòng lặp bắt 401, tránh đệ quy vô hạn.
  • Tôi biết test có router.navigate() cần route đích tồn tại thật.

7. Câu hỏi tư duy

AuthInterceptor gọi this.auth.accessToken và this.auth.logout() — nhưng AuthService hiện tại của bạn (từ Bài 13) chỉ có isLoggedIn/login()/logout() tối thiểu, không có khái niệm access token hay currentUser$ để component khác subscribe.

Header hiển thị tên người dùng, trang Profile hiển thị thông tin đầy đủ, Guard kiểm role — tất cả cần đọc trạng thái đăng nhập hiện tại, nhưng theo những cách khác nhau (một lần đọc snapshot, một luồng subscribe liên tục).
