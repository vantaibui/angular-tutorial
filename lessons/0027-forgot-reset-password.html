1. Bài toán thật: xác thực người dùng CHƯA đăng nhập được

Người dùng quên mật khẩu. Họ chưa có access token, chưa có currentUser — mọi thứ ở Bài 24–26 đều giả định đã đăng nhập. Luồng ở đây phải đứng ngoài toàn bộ hệ thống auth đó:

  1. Nhập email → server gửi (giả lập) một email chứa link đặt lại.
  2. Link dạng /reset-password?token=abc123 — token không phải là định danh tài nguyên như /courses/:id, nó là một vé xác thực tạm thời.
  3. Component đọc token đó, gọi API đổi mật khẩu.
🤔 Trước khi nhìn lời giải

/reset-password/:token (path param) và /reset-password?token=... (query param) đều chạy được về mặt kỹ thuật. Vậy chọn theo tiêu chí nào?

💡 Hãy giữ câu này trong đầu

Token đặt lại mật khẩu không định danh "trang reset-password nào" — nó là một mẩu dữ liệu ĐI KÈM route đó. Route vẫn hợp lệ dù thiếu token; chỉ là bạn phải TỰ xử lý khi thiếu.

Đây chính xác là logic bạn đã dùng cho returnUrl ở Bài 13 — cùng một khái niệm, áp dụng lần thứ hai.

3. Code

TypeScript · src/app/core/services/password-reset.service.ts 
@Injectable({ providedIn: 'root' })
export class PasswordResetService {
  private readonly http = inject(HttpClient);

  requestReset(email: string): Observable<{ message: string }> {
    return this.http.post<{ message: string }>('/api/auth/forgot-password', { email });
  }

  resetPassword(token: string, newPassword: string): Observable<{ message: string }> {
    return this.http.post<{ message: string }>('/api/auth/reset-password', { token, newPassword });
  }
}
TypeScript · reset-password.component.ts — 4 trạng thái rõ ràng 
export class ResetPasswordComponent implements OnInit {
  private readonly route = inject(ActivatedRoute);
  private readonly svc = inject(PasswordResetService);
  private readonly fb = inject(FormBuilder);

  private token: string | null = null;
  // 4 trạng thái tường minh — KHÔNG dùng vài boolean rời rạc dễ tạo ra tổ hợp vô nghĩa
  // (vd loading=true VÀ error=true cùng lúc, template phải đoán ưu tiên cái nào).
  trangThai: 'nhap' | 'thieu-token' | 'thanh-cong' | 'het-han' = 'nhap';

  form = this.fb.group({
    newPassword: ['', [Validators.required, Validators.minLength(8)]],
  });

  ngOnInit(): void {
    // queryParamMap, KHÔNG phải paramMap (đó là cho path param) — nhầm lẫn hay gặp nhất bài.
    this.token = this.route.snapshot.queryParamMap.get('token');
    if (!this.token) this.trangThai = 'thieu-token';
  }

  submit(): void {
    if (this.form.invalid || !this.token) return;
    this.svc.resetPassword(this.token, this.form.value.newPassword!).subscribe({
      next: () => { this.trangThai = 'thanh-cong'; },
      error: () => { this.trangThai = 'het-han'; },  // server trả 400 khi token không hợp lệ/hết hạn
    });
  }
}
🔥 route.paramMap vs route.queryParamMap — nhầm là ra null mãi mãi

Cả hai đều tồn tại trên ActivatedRoute, cả hai đều có .get('token'), và TypeScript không hề báo lỗi nếu bạn gõ nhầm — chỉ là bạn luôn nhận null một cách bí ẩn dù URL rõ ràng có ?token=abc. Query param luôn nằm ở queryParamMap, path param (/:id) nằm ở paramMap.

4. Vì sao "thiếu token" và "hết hạn" phải là hai trạng thái riêng

⚖️ Không được gộp thành một thông báo "Có lỗi xảy ra"

Hai tình huống có nguyên nhân và hành động tiếp theo khác hẳn nhau:

Trạng tháiNguyên nhânNgười dùng nên làm gì
thieu-tokenVào thẳng URL không qua email (gõ tay, hoặc link bị cắt cụt)Quay lại trang "Quên mật khẩu", xin lại đúng cách
het-hanToken từng hợp lệ nhưng đã dùng rồi hoặc quá hạnYêu cầu gửi lại email — link cũ không cứu được nữa

Thông báo chung chung "Có lỗi xảy ra" bắt người dùng tự đoán phải làm gì tiếp — họ sẽ thử bấm nút vài lần rồi bỏ cuộc.

http.post('*/api/auth/forgot-password', async ({ request }) => {
  const body = await request.json() as { email: string };

🔥 Bug bảo mật kinh điển: form "quên mật khẩu" thành công cụ dò email

Nếu API trả lỗi khác nhau cho "email không tồn tại" so với "email tồn tại, đã gửi", kẻ tấn công thử hàng loạt email và biết chính xác email nào có tài khoản trong hệ thống — vi phạm quyền riêng tư của người dùng dù không hề chạm được vào mật khẩu. Luôn trả về cùng một thông báo bất kể email có tồn tại hay không.

6. Test — cả 2 case token, không dựng Router thật

TypeScript · test đã verify xanh 
function setup(queryToken: string | null) {
  TestBed.configureTestingModule({
    imports: [TestHostModule],
    providers: [
      provideHttpClient(), provideHttpClientTesting(),
      {
        // Không cần Router THẬT — chỉ cần ĐÚNG shape mà component đọc: snapshot.queryParamMap.
        provide: ActivatedRoute,
        useValue: { snapshot: { queryParamMap: convertToParamMap(queryToken ? { token: queryToken } : {}) } },
      },
    ],
  });
  const fixture = TestBed.createComponent(ResetPasswordComponent);
  fixture.detectChanges();
  return { fixture, httpMock: TestBed.inject(HttpTestingController) };
}

it('thiếu token trên query param -> báo lỗi ngay, không hiện form', () => {
  const { fixture } = setup(null);
  expect(fixture.componentInstance.trangThai).toBe('thieu-token');
  expect(fixture.nativeElement.querySelector('form')).toBeNull();
});

it('token hết hạn -> server trả 400, hiện thông báo hết hạn', async () => {
  const { fixture, httpMock } = setup('token-cu-da-het-han');
  const cmp = fixture.componentInstance;
  cmp.form.setValue({ newPassword: 'MatKhauMoi123' });
  cmp.submit();

  httpMock.expectOne('/api/auth/reset-password')
    .flush({ message: 'expired' }, { status: 400, statusText: 'Bad Request' });

  await Promise.resolve();
  expect(cmp.trangThai).toBe('het-han');
});
🔎 Vì sao override ActivatedRoute bằng useValue thay vì RouterTestingModule

Component chỉ đọc đúng một đường: route.snapshot.queryParamMap.get('token'). Cung cấp một object giả có đúng hình dạng đó là đủ — nhẹ hơn nhiều so với dựng cả Router thật (như Bài 13 phải làm, vì ở đó cần test điều hướng thật sự xảy ra). Chọn công cụ test theo đúng thứ đang được kiểm tra.
