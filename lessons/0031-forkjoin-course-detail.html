Trang chi tiết khoá học cần 3 API độc lập cùng lúc — và một API chết không được phép kéo sập hai API còn lại. Dùng lại GenericListComponent vừa xây ở Bài 30.

🎯 Sau bài này bạn phải làm được
  • Dùng forkJoin để gọi N Observable song song và gộp kết quả thành một object.
  • Giải thích vì sao forkJoin thất bại HOÀN TOÀN nếu một nhánh lỗi, và đặt catchError đúng chỗ (TRONG từng nhánh) để chặn việc đó.
  • Nhận diện tình huống zoneless cần markForCheck() thủ công — khi component không thể dùng | async vì cần thêm trạng thái loading tự quản lý.

Bài 01: Observable lỗi là kết thúc, không có "bỏ qua rồi tiếp". Bài 27: path param (:id) bắt buộc để route khớp, khác hẳn query param tuỳ chọn. Bài 30: GenericListComponent<T> dùng chung cho mọi danh sách. Bài 16 mục 5 / Bài 29: zoneless cần được "báo" khi state đổi ngoài sự kiện template.

Bài này ghép cả bốn lại trong một component thật: CourseDetailComponent.

1. Bài toán thật: 3 API độc lập, 1 màn hình

Trang chi tiết khoá học cần: thông tin khoá học (GET /api/courses/:id), danh sách đánh giá (GET /api/courses/:id/reviews), và khoá học liên quan (GET /api/courses?exclude=:id&limit=4). Ba API này không phụ thuộc lẫn nhau — gọi tuần tự (cái này xong mới gọi cái kia) chỉ làm trang load chậm vô ích.

Nhưng có rủi ro thật: nếu server đánh giá đang lỗi, người dùng vẫn nên xem được khoá học và mua nó — không nên vì một phần phụ chết mà cả trang trắng xoá.

🤔 Trước khi nhìn lời giải

Bạn cần một toán tử gộp N Observable song song (không phải tuần tự như switchMap lồng nhau) thành MỘT kết quả tổng hợp. Nhưng nhớ lại Bài 01: một Observable lỗi thì kết thúc luôn, không phát tiếp giá trị nào. Nếu toán tử gộp thừa hưởng đúng tính chất đó, một nhánh lỗi sẽ ảnh hưởng gì tới TOÀN BỘ kết quả gộp?

2. Mental model: forkJoin fail-fast — và cách "cách ly" từng nhánh

TypeScript · ❌ forkJoin trần trụi — 1 nhánh lỗi, mất cả 2 nhánh kia 
forkJoin({
  course: this.courseService.getById(id),
  reviews: this.courseService.getReviews(id),   // server lỗi 500
  related: this.courseService.getAll({ exclude: id, limit: 4 }),
}).subscribe(...);
// reviews lỗi -> forkJoin lỗi NGAY LẬP TỨC -> .subscribe(...) không bao giờ chạy tới,
// dù course và related đã fetch THÀNH CÔNG từ lâu. Đây là hệ quả trực tiếp của Bài 01.
✅ Lời giải: catchError TRONG TỪNG NHÁNH, forkJoin không bao giờ thấy lỗi 
forkJoin({
  course: this.courseService.getById(id).pipe(catchError(() => of(null))),
  reviews: this.courseService.getReviews(id).pipe(catchError(() => of([] as Review[]))),
  related: this.courseService.getAll({ exclude: id, limit: 4 }).pipe(catchError(() => of(EMPTY_LIST))),
}).subscribe(({ course, reviews, related }) => { ... });
// Mỗi nhánh TỰ bắt lỗi của CHÍNH NÓ, thay lỗi bằng một giá trị fallback an toàn.
// forkJoin nhìn thấy 3 Observable đều "thành công" (dù reviews thực chất vừa lỗi) -> luôn gộp được.

Đây là bài học "đặt catchError trong hay ngoài" từ Bài 01 (và Bài 25 ở tầng interceptor) quay lại lần thứ ba: vị trí của catchError quyết định phạm vi nó bắt lỗi. Đặt NGOÀI forkJoin chỉ bắt được lỗi của chính forkJoin (đã quá muộn — nó đã lỗi rồi). Đặt TRONG từng nhánh chặn lỗi trước khi nó kịp lan tới forkJoin.

3. Code đầy đủ

TypeScript · src/app/features/courses/course-detail/course-detail.component.ts 
export interface CourseDetailData {
  course: Course | null;
  reviews: Review[];
  related: Course[];
}

const EMPTY_LIST = { data: [] as Course[], meta: { page: 1, limit: 4, total: 0, totalPages: 1 } };

@Component({ selector: 'app-course-detail', standalone: false, templateUrl: './course-detail.component.html' })
export class CourseDetailComponent implements OnInit {
  data: CourseDetailData | null = null;
  loading = true;

  constructor(
    private readonly courseService: CourseService,
    private readonly route: ActivatedRoute,
    private readonly cdr: ChangeDetectorRef,
  ) {}

  ngOnInit(): void {
    // :id là PATH param (Bài 27) — thiếu nó thì route còn không khớp, khác hẳn query param tuỳ chọn.
    const id = this.route.snapshot.paramMap.get('id')!;

    forkJoin({
      course: this.courseService.getById(id).pipe(catchError(() => of(null))),
      reviews: this.courseService.getReviews(id).pipe(catchError(() => of([] as Review[]))),
      related: this.courseService.getAll({ exclude: id, limit: 4 }).pipe(catchError(() => of(EMPTY_LIST))),
    }).subscribe(({ course, reviews, related }) => {
      this.data = { course, reviews, related: related.data };
      this.loading = false;
      this.cdr.markForCheck();  // zoneless (Bài 16/29) — .subscribe() thủ công, không có | async lo hộ
    });
  }
}

4. Phát hiện khi tôi verify bài này — markForCheck() lại xuất hiện

🔥 Vì sao KHÔNG dùng | async ở đây như Bài 29?

CourseDetailComponent cần một trạng thái loading riêng để phân biệt "đang tải" / "không tìm thấy" / "có dữ liệu" — ba nhánh hiển thị khác hẳn nhau. forkJoin chỉ phát ĐÚNG MỘT LẦN khi cả 3 nhánh xong (khác result$ ở Bài 29, có thể phát lại nhiều lần theo filter) nên | async vẫn dùng được, nhưng bạn vẫn cần một field loading để biết REQUEST đã xong hay chưa — và cách tự nhiên nhất để cập nhật nó là trong .subscribe(), ngoài mọi sự kiện template.

Tôi viết component KHÔNG có markForCheck() trước, chạy test: state (this.data, this.loading) đúng 100%, nhưng DOM sau detectChanges() lần hai vẫn hiện "Đang tải..." mãi — y hệt bug đã thấy ở Bài 28/29, lần này trong bối cảnh forkJoin thay vì combineLatest.

Đây là bằng chứng quy tắc Bài 16 mục 5 tổng quát hơn những gì bạn nghĩ ban đầu: nó không chỉ áp dụng cho ControlValueAccessor. Bất kỳ đâu bạn tự .subscribe() một Observable (không qua | async) trong app zoneless, bạn cần tự hỏi: "callback này có chạy TRONG một event template không?" — nếu không, phải markForCheck().

TypeScript · test tái hiện bug (đã verify — thất bại nếu thiếu markForCheck) 
httpMock.expectOne('/api/courses/course_1').flush({ message: 'not found' }, { status: 404, statusText: 'Not Found' });
httpMock.expectOne('/api/courses/course_1/reviews').flush([]);
httpMock.expectOne((r) => r.params.get('exclude') === 'course_1').flush({ data: [], meta: {...} });

fixture.detectChanges();
expect(fixture.componentInstance.loading).toBe(false);       // ✅ state đúng, kể cả KHÔNG có markForCheck
expect(fixture.nativeElement.querySelector('.not-found')).not.toBeNull();  // ❌ đỏ nếu thiếu markForCheck() — DOM vẫn hiện "Đang tải..."

7. Câu hỏi tư duy

Trang chi tiết khoá học giờ có nút "Thêm vào giỏ hàng". Để cảm giác nhanh, bạn muốn UI cập nhật NGAY khi bấm (hiện badge giỏ hàng +1) — không đợi server xác nhận. Nhưng nếu server từ chối (ví dụ khoá học đã bị gỡ), bạn phải "lùi lại" badge đó về giá trị cũ.

Đây khác hẳn mọi thứ Module 6 vừa làm: cho tới giờ, UI luôn đợi API trả lời rồi mới hiển thị (loading → data). Giờ bạn cần UI đi TRƯỚC server, và có kế hoạch "quay xe" nếu đoán sai.

Thiết kế nào cho phép "cập nhật UI trước, xác nhận với server sau, và lùi lại nếu server từ chối" — mà không làm rối state của cả app?
