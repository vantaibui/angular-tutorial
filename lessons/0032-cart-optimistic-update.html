CartService — optimistic update + rollback

Bấm "Thêm vào giỏ" phải cảm giác NGAY LẬP TỨC, không đợi server. Nhưng nếu server từ chối, UI phải "lùi lại" đúng như chưa có gì xảy ra.

⏱ ~40 phút · 🎯 Mở Module 7 — state management bắt đầu đau, chuẩn bị nền cho NgRx

🎯 Sau bài này bạn phải làm được
  • Giải thích chính xác "optimistic update" nghĩa là gì và đánh đổi gì so với chờ server trước.
  • Lưu lại state CŨ trước khi đổi, để có gì "lùi về" khi server từ chối.
  • Viết test chứng minh CẢ HAI chiều: cập nhật tức thời VÀ rollback khi lỗi — thiếu một trong hai là bài chưa xong.
🌉 Bắc cầu từ cái bạn đã biết

Bài 03 / Bài 26: BehaviorSubject giữ "giá trị hiện tại", đọc snapshot qua .value. Bài này dùng chính .value đó cho việc khác: chụp lại state TRƯỚC khi thay đổi, để có bản sao lưu phòng khi cần lùi lại.

1. Bài toán thật: chờ server thì chậm, không chờ thì rủi ro

Cách "an toàn" nhất: bấm nút → gọi API → đợi phản hồi → MỚI cập nhật UI. Nhưng với hành động nhỏ như "thêm vào giỏ", vài trăm mili-giây chờ đợi đó cảm giác ì ạch — người dùng mong UI phản hồi ngay khi họ bấm.

Vấn đề: nếu bạn cập nhật UI ngay LẬP TỨC (trước khi biết server có đồng ý hay không), và server sau đó từ chối (ví dụ: khoá học này người dùng đã mua rồi), UI đang nói dối — nó hiển thị một trạng thái mà server không công nhận.

🤔 Trước khi nhìn lời giải

Muốn "lùi lại" một thay đổi, bạn cần biết trạng thái TRƯỚC khi thay đổi đó xảy ra. Có công cụ nào trong tay bạn đã dùng suốt khoá học này luôn giữ sẵn "giá trị hiện tại", đọc được bất cứ lúc nào mà không cần subscribe?

2. Mental model: chụp lại, đổi ngay, lùi nếu cần

Ba bước cố định, mọi optimistic update đều theo khuôn này 
// BƯỚC 1 — chụp lại state CŨ (trước khi đổi bất cứ gì)
const previous = this.itemsSubject.value;

// BƯỚC 2 — đổi NGAY, không đợi server (đây là phần "optimistic")
this.itemsSubject.next([...previous, item_moi]);

// BƯỚC 3 — gọi API thật; nếu THÀNH CÔNG thì không làm gì thêm (state đã đúng từ Bước 2);
// nếu THẤT BẠI thì .next(previous) — LÙI VỀ đúng snapshot đã chụp ở Bước 1.

Đây là lý do .value của BehaviorSubject (Bài 03) quan trọng hơn bạn nghĩ lúc đầu: nó không chỉ để "đọc nhanh không cần subscribe", nó còn là công cụ chụp snapshot cho optimistic update.

3. Code đầy đủ

TypeScript · src/app/core/services/cart.service.ts 
@Injectable({ providedIn: 'root' })
export class CartService {
  private readonly http = inject(HttpClient);
  private readonly itemsSubject = new BehaviorSubject<CartItem[]>([]);

  readonly items$ = this.itemsSubject.asObservable();
  get items(): CartItem[] { return this.itemsSubject.value; }

  addToCart(courseId: string): Observable<void> {
    const previous = this.itemsSubject.value;
    if (previous.some((item) => item.courseId === courseId)) {
      return of(undefined); // đã có trong giỏ — không optimistic, không gọi API thừa
    }

    // OPTIMISTIC: cập nhật UI NGAY, chưa đợi server xác nhận.
    const optimisticItem: CartItem = { courseId, addedAt: new Date().toISOString() };
    this.itemsSubject.next([...previous, optimisticItem]);

    return this.http.post<CartItem>('/api/cart', { courseId }).pipe(
      map(() => undefined),
      catchError((err) => {
        this.itemsSubject.next(previous); // ROLLBACK: server từ chối -> lùi lại state cũ
        return throwError(() => err);
      }),
    );
  }

  removeFromCart(courseId: string): Observable<void> {
    const previous = this.itemsSubject.value;
    this.itemsSubject.next(previous.filter((item) => item.courseId !== courseId)); // OPTIMISTIC

    return this.http.delete<void>(`/api/cart/${courseId}`).pipe(
      catchError((err) => {
        this.itemsSubject.next(previous); // ROLLBACK
        return throwError(() => err);
      }),
    );
  }
}
🔥 Vì sao addToCart vẫn trả về Observable<void> có thể lỗi

Rollback xảy ra bên trong service — state luôn đúng dù component gọi có xử lý lỗi hay không. Nhưng component vẫn cần biết việc thêm vào giỏ đã thất bại để hiện thông báo ("Không thể thêm — bạn đã mua khoá học này rồi"). Tách hai việc: service lo ĐÚNG STATE, component lo THÔNG BÁO NGƯỜI DÙNG.

🔥 Vì sao kiểm tra trùng courseId TRƯỚC khi optimistic, không phải sau

Nếu không kiểm tra, bấm 2 lần liên tiếp vào cùng một khoá học sẽ optimistic thêm 2 lần (UI hiện 2 dòng giống hệt nhau) trước khi request đầu kịp trả lời. Kiểm tra previous.some(...) trước khi làm bất cứ gì biến việc này thành no-op an toàn.
