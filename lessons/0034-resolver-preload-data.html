Resolver — preload data trước khi vào route

Guard trả lời "được vào không?". Resolver trả lời câu hỏi khác: "vào thì mang gì theo?" — dữ liệu sẵn sàng TRƯỚC khi component tồn tại, không phải spinner rồi render lại.

⏱ ~35 phút · 🎯 Class-based Resolve<T> — nối lại Bài 08, Bài 13

🎯 Sau bài này bạn phải làm được
  • Viết một class implements Resolve<T>, gắn vào route qua resolve: { key: Resolver }.
  • Đọc dữ liệu đã resolve qua route.snapshot.data['key'] — và biết nó CHẮC CHẮN có mặt khi ngOnInit chạy.
  • Test được route có resolver mà không làm treo test (deadlock thật đã gặp khi soạn bài này).
🌉 Bắc cầu từ cái bạn đã biết

Bài 13: Guard là class, chạy TRƯỚC khi route kích hoạt, quyết định boolean/UrlTree. Bài 08: route.data là Record<string, any> — nơi bạn đọc thứ gì đó đã được "gắn" sẵn vào route. Resolver là mảnh ghép nối hai điều đó: nó cũng chạy TRƯỚC khi route kích hoạt (như Guard), nhưng thay vì trả boolean, nó trả DỮ LIỆU — và dữ liệu đó được Angular tự động gắn vào đúng chỗ bạn đã quen đọc: route.data.

1. Bài toán thật: "sẵn sàng trước" khác "tải xong rồi mới hiện"

Cách quen thuộc bạn đã làm suốt khoá học (Bài 09-11, 28-31): component vào ngOnInit, gọi API, hiện spinner, nhận data, render. Cách này ổn cho hầu hết trường hợp — nhưng với bước "Mã giảm giá" trong checkout, danh sách coupon RẤT nhỏ và bạn muốn màn hình hiện ra đã có sẵn dữ liệu, không có khung hình "đang tải" chớp qua rồi biến mất ngay.

🤔 Trước khi nhìn lời giải

Guard (Bài 13) chứng minh Angular Router CÓ THỂ chạy code TRƯỚC khi component được tạo, và CHỜ code đó xong (nếu nó trả Observable) trước khi tiếp tục điều hướng. Nếu thay vì trả về boolean, đoạn code đó trả về DỮ LIỆU — dữ liệu đó có thể "đi" tới đâu để component đọc được ngay khi vừa sinh ra?

2. Viết CouponResolver

TypeScript · src/app/features/checkout/coupon.resolver.ts 
@Injectable({ providedIn: 'root' })
export class CouponResolver implements Resolve<Coupon[]> {
  private readonly http = inject(HttpClient);

  resolve(): Observable<Coupon[]> {
    // Lỗi ở đây KHÔNG nên chặn cả bước checkout — coi như "không có coupon nào" thay vì crash route.
    return this.http.get<Coupon[]>('/api/coupons').pipe(catchError(() => of([])));
  }
}
TypeScript · gắn vào route 
{ path: 'coupon', component: CouponStepComponent, resolve: { coupons: CouponResolver } }
-- key "coupons" chính là TÊN sẽ xuất hiện trong route.snapshot.data

Giống hệt cấu trúc AuthGuard implements CanActivate ở Bài 13: một class, @Injectable({ providedIn: 'root' }), gắn thẳng vào route config — không phải hàm tự do (đó là kiểu Modern ResolveFn, dành cho Phase 14).

🔥 Vì sao catchError ở ĐÂY quan trọng hơn bạn nghĩ

Nếu resolve() trả về một Observable LỖI (không có catchError), Router sẽ COI ĐÓ LÀ ĐIỀU HƯỚNG THẤT BẠI — người dùng bị kẹt, không vào được route coupon luôn, kể cả khi lỗi chỉ là "server coupon tạm thời chậm". Với dữ liệu KHÔNG QUAN TRỌNG SỐNG CÒN (coupon là tính năng phụ, không phải trung tâm), fallback về mảng rỗng tốt hơn nhiều so với chặn đứng cả luồng checkout.

3. Đọc dữ liệu đã resolve trong component

TypeScript · coupon-step.component.ts 
export class CouponStepComponent implements OnInit {
  validCoupons: Coupon[] = [];

  constructor(private readonly route: ActivatedRoute, readonly checkoutState: CheckoutStateService) {}

  ngOnInit(): void {
    // route.data là Record<string, any> (Bài 08) — đọc đúng KEY đã khai trong route.resolve.
    const coupons = (this.route.snapshot.data['coupons'] as Coupon[]) ?? [];
    const now = Date.now();
    this.validCoupons = coupons.filter((c) => new Date(c.expiresAt).getTime() > now && c.usedCount < c.maxUses);
  }
}

Không một dòng HttpClient nào trong component này — nó tin tưởng tuyệt đối rằng route.snapshot.data['coupons'] đã có mặt khi ngOnInit chạy. Đây chính là điểm khác biệt với cách "tự fetch trong ngOnInit": component không cần biết dữ liệu TỚI TỪ ĐÂU, chỉ cần biết Router đã chuẩn bị sẵn.

🔥 Bẫy gõ nhầm — lặp lại nguyên văn cảnh báo Bài 08

route.data là Record<string, any> — TypeScript KHÔNG báo lỗi nếu bạn gõ nhầm route.snapshot.data['coupon'] (thiếu chữ "s") thay vì 'coupons'. Kết quả: undefined, ?? [] âm thầm trả về mảng rỗng, màn hình "không có coupon nào" dù server có dữ liệu thật. Không có lỗi biên dịch, không có lỗi runtime — chỉ có hành vi sai lặng lẽ.

4. Chứng minh bằng test — và một deadlock thật

TypeScript · ❌ thử đầu tiên — TREO tới khi hết timeout 
const harness = await RouterTestingHarness.create('/checkout/coupon');
httpMock.expectOne('/api/coupons').flush(RAW_COUPONS); // KHÔNG BAO GIỜ chạy tới dòng này
🔥 Bug thật tôi gặp khi soạn bài này — deadlock giữa await và flush()

RouterTestingHarness.create(url) nội bộ gọi await router.navigateByUrl(url) — Promise đó CHỈ resolve SAU KHI resolver (và HTTP request bên trong nó) hoàn tất. Nếu bạn viết const harness = await RouterTestingHarness.create(...) rồi MỚI tìm request để flush, code không bao giờ chạy tới dòng flush() — vì dòng đó nằm SAU await, mà chính request đang chờ được flush lại là thứ khiến await không bao giờ xong. Một deadlock cổ điển giữa hai bên cùng chờ nhau.

TypeScript · ✅ lời giải — TÁCH Promise ra, flush TRƯỚC KHI await 
const createPromise = RouterTestingHarness.create('/checkout/coupon');  // KHÔNG await ngay
await new Promise((r) => setTimeout(r));  // nhường vòng lặp sự kiện, để loadChildren + resolver kịp bắn request
httpMock.expectOne('/api/coupons').flush(RAW_COUPONS);      // giờ request ĐÃ tồn tại, flush được
const harness = await createPromise;                          // bây giờ mới await -> resolve bình thường

Nguyên tắc chung khi test bất kỳ thao tác async nào có PHỤ THUỘC HAI CHIỀU (code chờ request, request chờ bạn flush): đừng await ngay lập tức. Giữ Promise lại, làm việc cần làm (flush request đang treo), RỒI mới await.
