Bài này là nơi cả bốn gặp nhau trong MỘT tính năng — và như mọi lần tích hợp thật, có những chỗ không khớp hoàn hảo ngay từ đầu.

1. Bài toán thật: một component, hai chế độ

Trang admin cần: danh sách khoá học, nút "Tạo mới", nút "Sửa" trên mỗi dòng. Cả tạo mới lẫn sửa đều cùng MỘT bộ field (tiêu đề, giá, mô tả, trình độ) — khác nhau đúng một điều: sửa thì form phải có sẵn dữ liệu cũ, tạo mới thì rỗng.

Route /admin/courses/new và /admin/courses/:id/edit cùng trỏ vào MỘT AdminCourseFormComponent — phân biệt bằng việc :id có mặt hay không (path param, Bài 27).

2. Route admin — tái dùng nguyên xi RoleGuard

TypeScript · admin-routing.module.ts 
const routes: Routes = [
  {
    path: 'courses',
    canActivate: [RoleGuard],       // y hệt Bài 14 — không viết guard mới
    data: { roles: ['admin'] },
    children: [
      { path: '', component: AdminCourseTableComponent },  // Bài 39 sẽ nâng cấp thành CDK Table
      { path: 'new', component: AdminCourseFormComponent },
      { path: ':id/edit', component: AdminCourseFormComponent },
    ],
  },
];

Đặt canActivate: [RoleGuard] ở route CHA ('courses') — áp dụng cho MỌI route con (danh sách, tạo mới, sửa) mà không cần lặp lại ở từng route con. Guard chạy MỘT LẦN khi vào /admin/courses hoặc bất kỳ route con nào của nó.

3. Ráp DynamicFormComponent — và hố nứt đầu tiên

TypeScript · src/app/features/admin/admin-course-form/course-schema.ts 
export const courseSchema: FormFieldSchema<Course>[] = [
  { name: 'title', label: 'Tiêu đề', type: 'text', validators: [Validators.required] },
  { name: 'price', label: 'Giá (USD)', type: 'number', validators: [Validators.required, Validators.min(0)] },
  { name: 'level', label: 'Trình độ', type: 'select', options: [...] },
];
🔥 Phát hiện khi tôi verify bài này — DynamicFormComponent (Bài 22) không nhận được schema có kiểu

Bài 22 khai @Input() schema: FormFieldSchema[] = [] — KHÔNG generic. Gán courseSchema (kiểu FormFieldSchema<Course>[]) vào đó ra lỗi biên dịch thật: Course không tự khớp Record<string, unknown> — một quirk TypeScript kinh điển: interface cụ thể không có index signature thì KHÔNG được coi là tương thích với kiểu có index signature, dù về mặt cấu trúc mọi field đều hợp lệ. Bài 22 chưa bao giờ thử gán một schema CÓ KIỂU thật vào component, nên hố nứt này chưa từng lộ ra.

TypeScript · sửa: generic hoá DynamicFormComponent 
export class DynamicFormComponent<TModel = Record<string, unknown>> implements OnInit, OnChanges {
  @Input({ required: true }) schema: FormFieldSchema<TModel>[] = [];
  ...
}
🔥 Sửa xong lại lộ hố nứt THỨ HAI — kiểu rò vào template

Generic hoá xong, field.name trong TEMPLATE có kiểu keyof TModel — với TModel không ràng buộc, đó là string | number | symbol. form.get(field.name) và [formControlName]="field.name" đều đòi string thuần, không nhận symbol lẫn vào. Lỗi biên dịch TEMPLATE, không phải class.

TypeScript · lời giải: ép kiểu MỘT LẦN qua method, không rải rác trong template 
fieldName(field: FormFieldSchema<TModel>): string {
  return field.name as string;
}
HTML · template gọi qua method, KHÔNG đọc field.name trực tiếp 
<input [id]="fieldName(field)" [formControlName]="fieldName(field)" ... />

Đây là bài học thực dụng: generic mạnh mẽ ở chỗ khai báo (schema), nhưng khi generic đó chưa ràng buộc gì (TModel không extends gì cả), phần dùng bên trong (template) phải tự ép kiểu tường minh ở đúng MỘT chỗ, không để nó rò ra khắp nơi.

4. Hố nứt thứ ba: initialValue tới SAU, và ngOnChanges

TypeScript · admin-course-form.component.ts 
export class AdminCourseFormComponent implements OnInit {
  readonly schema = courseSchema;
  initialValue: Record<string, unknown> = {};
  private courseId: string | null = null;

  ngOnInit(): void {
    this.courseId = this.route.snapshot.paramMap.get('id');
    if (this.courseId) {
      this.courseService.getById(this.courseId).subscribe((course) => {
        this.initialValue = course as unknown as Record<string, unknown>;
        this.cdr.markForCheck(); // xem callout dưới — quan trọng hơn bạn nghĩ
      });
    }
  }
}

Ở chế độ SỬA, initialValue bắt đầu là {} (rỗng, lúc ngOnInit chạy) rồi được GÁN LẠI sau khi getById() trả lời — bất đồng bộ. DynamicFormComponent (Bài 22) chỉ dựng form MỘT LẦN ở ngOnInit của CHÍNH NÓ — form con sẽ mãi mãi rỗng nếu không có thêm gì.

TypeScript · thêm ngOnChanges vào DynamicFormComponent 
ngOnChanges(changes: SimpleChanges): void {
  if (changes['initialValue'] && this.form) {
    this.form = this.buildForm(); // dựng LẠI form khi initialValue đổi giá trị SAU lần đầu
  }
}
🔥🔥 Phát hiện quan trọng nhất bài này — markForCheck() không chỉ ảnh hưởng view CỦA CHÍNH NÓ

Verify KHÔNG có markForCheck() trong subscribe callback: initialValue của AdminCourseFormComponent đúng giá trị (đọc field trực tiếp thấy dữ liệu mới), NHƯNG ngOnChanges của DynamicFormComponent con không hề được gọi — dù binding [initialValue]="initialValue" vẫn còn đó. Đây là điều mới so với mọi phát hiện markForCheck() trước (Bài 16/29/31/37): thiếu nó không chỉ khiến VIEW CỦA CHÍNH COMPONENT đứng yên — nó khiến Angular KHÔNG LAN TRUYỀN được thay đổi @Input xuống CON, nên ngOnChanges của con không chạy, dù property cha đã đúng 100%.

Xác minh bằng probe tối giản (host + child thuần, không HTTP/RxJS gì cả): gán thẳng property cha rồi gọi detectChanges() lần hai → ngOnChanges của con không chạy. Thêm đúng một dòng markForCheck() vào chỗ gán → chạy đúng ngay. Quy tắc từ giờ: bất kỳ đâu bạn mutate một field được BIND xuống component con từ một callback ngoài event template, markForCheck() không phải tuỳ chọn.

5. Hố nứt thứ tư (nhỏ hơn): submit mất kiểu ở ranh giới CRUD

TypeScript 
onSubmit(value: Record<string, unknown>): void {
  const request$ = this.courseId
    ? this.courseService.update(this.courseId, value as Partial<Course>)
    : this.courseService.create(value as unknown as Omit<Course, 'id'>);
  request$.subscribe(() => this.router.navigate(['/admin/courses']));
}

keyof (Bài 22) đảm bảo TÊN field trong schema đúng — nhưng giá trị component EMIT ra khi submit vẫn là Record<string, unknown> trần. Ranh giới với GenericApiService<Course>.create() (Bài 10, đòi Omit<Course,'id'> đầy đủ) luôn cần một cú ép kiểu. Đây là đánh đổi CHƯA được liệt kê ở Bài 22 mục 5 ("khi nào không nên dùng dynamic form") — chỉ lộ ra khi ráp dynamic form vào một CRUD service generic khác. Với form CHỈ SỬA MỘT PHẦN field (như ở đây), cách thực tế nhất là chấp nhận ép kiểu có kiểm soát tại đúng MỘT điểm nối, không lan ra toàn bộ component.
