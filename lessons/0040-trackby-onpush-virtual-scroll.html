2. trackBy — nhận diện "đây vẫn là hàng cũ"

TypeScript 
// CdkTable so khớp row theo THAM CHIẾU object mặc định. Server trả JSON mỗi lần là OBJECT MỚI
// (dù cùng id) -> không có trackBy, CdkTable coi đó là "khác hoàn toàn", huỷ + tạo lại <tr>.
readonly trackByCourseId = (_index: number, course: Course): string => course.id;
HTML 
<table cdk-table [dataSource]="courses" [trackBy]="trackByCourseId">
🔥 Phát hiện khi verify: thử sai kịch bản đầu tiên, tưởng đã chứng minh được nhưng chưa

Thử đầu tiên: sort lại MẢNG hiện có ([...this.courses].sort(...)) rồi kiểm DOM node có giữ nguyên không — giữ nguyên ngay cả khi KHÔNG có trackBy. Lý do: sort() chỉ đổi VỊ TRÍ trong mảng, các OBJECT course bên trong vẫn là CHÍNH NÓ (cùng tham chiếu) — CdkTable so khớp theo tham chiếu object MẶC ĐỊNH đã đúng rồi, chưa cần trackBy mới đúng.

trackBy chỉ thật sự cần khi dữ liệu tới từ một NGUỒN MỚI (gọi lại API) mà logic vẫn là "cùng một khoá học". Kịch bản đúng: xoá 1 dòng rồi load() gọi lại courseService.getAll() — response JSON MỚI, mỗi object course trong đó là INSTANCE MỚI dù id giống hệt. Đây mới là nơi trackBy tạo khác biệt.

TypeScript · test đã verify — kịch bản ĐÚNG 
it('trackBy giữ DOM row khi server trả OBJECT MỚI cùng id', () => {
  // Load lần 1: course 'c2' là OBJECT A
  const c2RowBefore = ...tìm <tr> chứa "RxJS"...;

  // Xoá c1 -> load() gọi lại getAll() -> server trả OBJECT B cho 'c2' (khác tham chiếu A)
  component.remove({ id: 'c1' });
  httpMock.expectOne('/api/courses/c1').flush(null);
  httpMock.expectOne(...).flush({ data: [{ id: 'c2', title: 'RxJS', ... }] }); // object B

  const c2RowAfter = ...tìm <tr> chứa "RxJS"...;
  expect(c2RowAfter).toBe(c2RowBefore); // CÙNG DOM node — trackBy nhận ra "vẫn là c2"
});

Xác minh đây là test canh gác thật: xoá [trackBy] khỏi template → test CHUYỂN ĐỎ ngay (c2RowAfter khác c2RowBefore — DOM bị huỷ tạo lại dù logic là "cùng course"). Thêm lại trackBy → xanh trở lại.

3. OnPush — điều kiện an toàn để bật

TypeScript 
@Component({
  selector: 'app-admin-course-table',
  standalone: false,
  templateUrl: './admin-course-table.component.html',
  // Điều kiện an toàn: MỌI chỗ đổi `courses` phải gán MẢNG MỚI, không mutate tại chỗ.
  // Đã đúng SẴN từ Bài 39 (spread trong sort, gán res.data mới trong load()) — không cần sửa gì.
  changeDetection: ChangeDetectionStrategy.OnPush,
})
export class AdminCourseTableComponent { ... }
OnPush check lại view khiĐã có sẵn trong component này?
Một @Input đổi REFERENCEComponent này không có @Input — không áp dụng
Một sự kiện template CỦA CHÍNH component (click, input)✅ onSort(), onSearchInput(), onPage() đều là (click)/(input)
markForCheck() được gọi tường minh✅ đã có trong load() — cho nhánh .subscribe() thủ công
💡 Vì sao bật OnPush ở đây "miễn phí"

Code từ Bài 39 vốn đã tuân thủ kỷ luật OnPush TỪ TRƯỚC — không phải vì cố ý, mà vì zoneless (Bài 16 mục 5) đòi hỏi ĐÚNG kỷ luật đó (gán mảng mới thay vì mutate, gọi markForCheck() sau .subscribe() thủ công). Đây là điểm hội tụ đã nhắc ở đầu bài: viết code đúng cho zoneless = viết code đã sẵn sàng cho OnPush. Bật cờ này không cần sửa một dòng logic nào.

🔥 Điều kiện an toàn — nếu KHÔNG tuân thủ thì đừng bật

Nếu component nào đó đổi dữ liệu bằng this.courses.push(item) (mutate tại chỗ, KHÔNG đổi reference) thay vì this.courses = [...this.courses, item], bật OnPush sẽ khiến view ĐỨNG YÊN dù dữ liệu đã đổi — vì OnPush so sánh THAM CHIẾU input, không so sánh nội dung bên trong.

4. Virtual scroll — giới thiệu, không sâu

trackBy và OnPush giảm việc THỪA khi RE-RENDER. Chúng không giải quyết một vấn đề khác: nếu bạn thật sự có 500 dòng và hiện HẾT một lúc (không phân trang), trình duyệt vẫn phải giữ 500 <tr> trong bộ nhớ — dù chỉ ~10 dòng nằm trong khung nhìn tại một thời điểm.

HTML · src/app/features/admin/virtual-course-list/virtual-course-list.component.ts 
<cdk-virtual-scroll-viewport itemSize="48" style="height: 400px">
  <div class="virtual-row" *cdkVirtualFor="let course of courses; trackBy: trackByCourseId">
    {{ course.title }}
  </div>
</cdk-virtual-scroll-viewport>

itemSize="48" báo cho CDK biết MỖI dòng cao bao nhiêu pixel — từ đó nó tính được "với khung nhìn cao 400px, cần khoảng bao nhiêu dòng DOM thật, còn lại chỉ là khoảng trống ảo để thanh cuộn đúng kích thước". *cdkVirtualFor hoạt động giống *ngFor nhưng CHỈ tạo DOM cho phần tử THẬT SỰ cần vẽ.

🔥 Giới hạn thật khi verify bài này — jsdom không tính layout

Cố gắng đếm chính xác số <div class="virtual-row"> được tạo ra trong test: LUÔN ra 0, kể cả sau khi ép getBoundingClientRect() trả về chiều cao 400px và gọi viewport.checkViewportSize() thủ công. jsdom không tính layout thật — CdkVirtualScrollViewport cần nhiều thông tin layout hơn những gì có thể giả lập gọn trong jsdom.

Quyết định thực dụng: test chỉ xác nhận component dựng ĐÚNG CẤU TRÚC CDK và KHÔNG THROW với 500 phần tử — việc "chỉ render dòng nhìn thấy" phải xác minh BẰNG MẮT trong trình duyệt thật (mở DevTools → Elements, cuộn, xem số node thay đổi). Nói thẳng giới hạn này thay vì viết một test trông có vẻ đúng nhưng không kiểm tra được điều nó tuyên bố.

Bạn vừa dùng markForCheck() ở ít nhất năm bài liên tiếp (Bài 16, 29, 31, 37, 38) — luôn cùng một lý do: mutate state trong .subscribe() thủ công, ngoài event template. Và bạn vừa thấy OnPush đòi hỏi ĐÚNG kỷ luật đó.

Có một câu hỏi chưa ai trả lời trong suốt hành trình này: Angular thực sự BIẾT "khi nào cần kiểm tra lại" bằng cơ chế gì? Bạn đã dùng markForCheck() như một "công tắc thủ công", nhưng chưa hiểu NÓ vận hành trên cơ chế nào bên dưới — Zone.js hoạt động ra sao ở Angular Classic, và app của bạn (zoneless từ Bài 00) thay thế nó bằng gì.
