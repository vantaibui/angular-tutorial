Phân tích bundle — nhìn thấy THẬT những gì nằm trong production bundle

Build xong không có nghĩa là biết bundle đang chứa gì. Bài này mổ xẻ bundle thật của một app Angular 22 — và phát hiện công cụ "chuẩn" nhiều năm nay (source-map-explorer) không còn chạy được với builder mới.

⏱ ~35 phút · 🎯 Đọc hiểu stats.json thật, không chỉ xem con số tổng

🎯 Sau bài này bạn phải làm được
  • Build production với --stats-json, tìm ĐÚNG vị trí file xuất ra (không nằm chỗ bạn nghĩ).
  • Đọc được stats.json để biết module NÀO đang chiếm bao nhiêu byte trong bundle.
  • Biết CHÍNH XÁC vì sao source-map-explorer — công cụ kinh điển cho Webpack — fail với builder esbuild của Angular 22.
🌉 Bắc cầu từ cái bạn đã biết

Bài 41-42 nhìn vào chi phí RUNTIME (bao nhiêu lần check lại). Bài này nhìn vào chi phí TẢI TRANG lần đầu — bao nhiêu KB trình duyệt phải tải trước khi EduCommerce chạy được dòng code đầu tiên. Hai loại chi phí hoàn toàn khác nhau, đo bằng công cụ khác nhau.

1. Build thật, số liệu thật

bash · kết quả chạy thật — app rỗng, chỉ có router + App component 
$ ng build --configuration production

Initial chunk files | Names   |  Raw size | Estimated transfer size
main-XCF7SOV6.js     | main    | 211.46 kB |                56.95 kB
styles-5INURTSO.css  | styles  |   0 bytes |                 0 bytes
                     | Initial total | 211.46 kB |          56.95 kB

App gần như RỖNG (không có feature nào của EduCommerce) đã nặng 211KB raw / ~57KB sau gzip. Đây không phải lỗi — đây là chi phí CỐ ĐỊNH của riêng Angular framework. Câu hỏi thật sự cần trả lời: trong 211KB đó, cái gì chiếm nhiều nhất?

2. --stats-json — và một bẫy vị trí file dễ đoán sai

bash 
$ ng build --configuration production --stats-json
🔥 Bẫy khi verify: file KHÔNG nằm trong thư mục browser/

Đoán tự nhiên: file xuất ra ở dist/<project>/browser/stats.json (cạnh main-*.js). SAI. Kiểm tra thật bằng find dist -iname "stats.json" → không thấy gì ở đó. File thật nằm ở: 

dist/cd-sandbox/browser-stats.json   ← CÙNG CẤP với thư mục browser/, không phải BÊN TRONG nó

Tên file là browser-stats.json (gạch nối, không phải thư mục) — dễ nhầm khi gõ tắt find . -path "*/browser/stats.json" rồi kết luận nhầm "tính năng này bị lỗi, không xuất ra gì".

3. Đọc stats.json — định dạng esbuild metafile

bash · kết quả chạy thật — top 5 module nặng nhất 
$ node -e "
const s = require('./dist/cd-sandbox/browser-stats.json');
Object.entries(s.inputs)
  .sort((a,b) => b[1].bytes - a[1].bytes)
  .slice(0,5)
  .forEach(([k,v]) => console.log(v.bytes, 'B |', k));
"

764310 B | .../@angular/core/fesm2022/core.mjs        ← @angular/core TỰ NÓ đã 764KB (trước minify)
170727 B | .../@angular/router/fesm2022/router.mjs
135211 B | .../@angular/core/fesm2022/... (chunk khác)
109501 B | .../@angular/core/fesm2022/... (chunk khác)
 99353 B | .../@angular/common/fesm2022/common.mjs

Số liệu này là kích thước TRƯỚC minify/tree-shaking cuối cùng (esbuild tính theo input module, không phải output đã nén) — nhưng vẫn cho thấy đúng TỶ LỆ: phần lớn 211KB thành phẩm là chính Angular framework (core + router + common), không phải code EduCommerce tự viết. Đây là baseline PHẢI CHẤP NHẬN — không tối ưu được bằng cách sửa code app.

JSON · cấu trúc thật của stats.json 
{
  "inputs": { "đường/dẫn/module.js": { "bytes": 12478, "imports": [...] }, ... },
  "outputs": { "main-XCF7SOV6.js": { ... } }
}

File này đúng định dạng esbuild metafile — kéo thả trực tiếp vào esbuild.github.io/analyze (công cụ CHÍNH THỨC, do Angular CLI tự trỏ tới trong ng build --help) để xem treemap trực quan, không cần cài thêm gì.

4. Vì sao source-map-explorer KHÔNG còn dùng được

source-map-explorer từng là công cụ chuẩn cho mọi hướng dẫn Angular Webpack nhiều năm qua. Thử trực tiếp trên bundle vừa build (có --source-map):

bash · kết quả chạy thật 
$ source-map-explorer dist/cd-sandbox/browser/main-*.js

dist/cd-sandbox/browser/main-CKVFZ5G6.js
  Your source map refers to generated column Infinity on line 1, but the source
  only contains 4414 column(s) on that line.
  Check that you are using the correct source map.

$ echo $?
1   ← FAIL thật, không phải warning vô hại
🔥 Nguyên nhân: giả định output nhiều dòng, esbuild xuất 1 dòng duy nhất

source-map-explorer (viết cho thời Webpack, bundle trải dài NHIỀU dòng) kỳ vọng source map ánh xạ theo (dòng, cột) với số dòng output tương ứng số dòng input. Bundle của esbuild (builder mặc định Angular 22) nén TOÀN BỘ output vào gần như MỘT dòng — khiến thư viện mapping cũ tính sai offset cột, vượt quá số cột thật trên dòng đó, rồi crash.

Đây KHÔNG phải lỗi cấu hình có thể sửa bằng flag — là một giới hạn thật sự giữa một công cụ viết cho kiến trúc bundler cũ và output của bundler mới. Dùng --stats-json + esbuild.github.io/analyze (mục 3) thay thế hoàn toàn, đây cũng chính là lý do Angular CLI tự trỏ người dùng tới công cụ đó thay vì source-map-explorer trong --help.

💡 Đọc treemap để làm gì trong EduCommerce thật

Khi áp dụng lên EduCommerce thật (không phải sandbox rỗng), mục tiêu là phát hiện: (1) thư viện ngoài nặng bất thường so với lợi ích nó mang lại (ví dụ: import cả một date-library lớn chỉ để format 1 kiểu ngày), (2) code của CHÍNH BẠN vô tình lọt vào bundle initial dù chỉ dùng ở một route hiếm khi vào (ứng viên tốt cho @defer — Bài 46), (3) duplicate — cùng một thư viện bị bundle 2 lần do version lệch nhau giữa các dependency.

6. Câu hỏi tư duy

Bạn vừa thấy 211KB cho một app gần như rỗng. Nhưng số đó chỉ là MỘT nửa câu chuyện — "nặng bao nhiêu KB" không nói lên "người dùng THẤY trang chạy được nhanh hay chậm". Hai app cùng 211KB có thể cho trải nghiệm tải trang HOÀN TOÀN khác nhau tuỳ cách chúng tải.

Nếu bundle size không phải thước đo trực tiếp trải nghiệm người dùng — vậy thước đo nào mới THẬT SỰ phản ánh "người dùng cảm thấy trang nhanh hay chậm"?
