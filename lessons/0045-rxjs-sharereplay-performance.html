RxJS + Performance — shareReplay, tránh subscribe thừa

Nối lại Bài 01-04. Cùng một bug "gọi API thừa" bạn từng thấy ở dạng khác — giờ nhìn đúng tên cơ chế đứng sau, và công cụ RxJS có sẵn để cắt nó.

⏱ ~30 phút · 🎯 Biết CHÍNH XÁC khi nào cần shareReplay, khi nào KHÔNG

🎯 Sau bài này bạn phải làm được
  • Chứng minh bằng thực nghiệm: 2 subscribe() vào cùng một Observable cold → 2 HTTP request thật.
  • Dùng shareReplay() đúng chỗ để biến N request thừa thành 1.
  • Biết rủi ro thật của shareReplay không cấu hình đúng — leak vì giữ subscription sống mãi.
🌉 Bắc cầu từ cái bạn đã biết

Bài 03 dạy "cold Observable" = công thức nấu ăn — mỗi subscribe() chạy lại từ đầu. Bài 01-02 dạy mỗi lần gọi http.get() là MỘT request riêng. Bài này ghép hai sự thật đó lại: http.get() trả về Observable CỐ MỖI lần subscribe là một request HTTP mới — kể cả khi 2 chỗ subscribe đó đang hỏi CÙNG một câu hỏi.

1. Bài toán thật: 2 chỗ trong component, cùng 1 nguồn, 2 request

CourseDetailComponent (Bài 31) có thể có courseDetail$ dùng ở CẢ template (| async) LẪN một chỗ khác trong TypeScript (ví dụ: ghi log, hoặc đẩy vào một service khác). Viết ngây thơ:

TypeScript · ❌ gọi API 2 lần mà không biết 
courseDetail$ = this.courseService.getById(this.id); // http.get() bên trong — COLD

ngOnInit() {
  this.courseDetail$.subscribe((c) => this.analytics.logView(c)); // subscribe #1
}
// template: {{ (courseDetail$ | async)?.title }}                      // subscribe #2

Nhìn qua tưởng chỉ có MỘT nguồn dữ liệu — thực tế courseDetail$ là cold, mỗi subscribe() chạy lại http.get() TỪ ĐẦU. Hai chỗ subscribe = HAI request HTTP riêng biệt tới cùng một endpoint, cùng tham số.

2. Chứng minh bằng thực nghiệm

TypeScript · src/playground/shareReplay-probe.spec.ts 
it('KHÔNG shareReplay: 2 subscribe -> 2 HTTP request thật', () => {
  const courses$ = http.get('/api/courses'); // cold

  courses$.subscribe();
  courses$.subscribe(); // subscribe LẦN 2 vào CÙNG courses$

  const reqs = httpMock.match('/api/courses');
  expect(reqs.length).toBe(2); // 2 REQUEST THẬT, không phải 1
});

it('CÓ shareReplay(1): 2 subscribe -> CHỈ 1 HTTP request duy nhất', () => {
  const courses$ = http.get('/api/courses').pipe(shareReplay(1));

  courses$.subscribe();
  courses$.subscribe();

  const reqs = httpMock.match('/api/courses');
  expect(reqs.length).toBe(1); // CHỈ 1 request, dù subscribe 2 lần
});
bash · kết quả chạy thật 
✓ KHÔNG shareReplay: 2 subscribe -> 2 HTTP request thật
✓ CÓ shareReplay(1): 2 subscribe -> CHỈ 1 HTTP request duy nhất

Test Files  1 passed (1)
     Tests  2 passed (2)

shareReplay(1) biến Observable COLD thành HOT (dùng chung MỘT subscription nội bộ tới nguồn gốc) VÀ "phát lại" (replay) giá trị cuối cho người subscribe SAU — người tới muộn vẫn thấy giá trị, không phải kích hoạt lại request. Đúng tinh thần "cold vs hot" Bài 03, áp dụng cho chính HTTP response.

3. Rủi ro thật — shareReplay không cấu hình đúng có thể leak

🔥 Bẫy: shareReplay mặc định KHÔNG tự huỷ khi hết subscriber

shareReplay(1) (không truyền config object) giữ subscription tới nguồn gốc SỐNG MÃI ngay cả khi TẤT CẢ subscriber đã huỷ (unsubscribe) — vì nó không biết "có nên ngắt kết nối nguồn khi không còn ai nghe" hay không. Với http.get() (complete sau 1 lần phát) ít nguy hiểm vì request đã xong sẽ tự complete. Nhưng với một stream SỐNG LÂU DÀI (WebSocket ở Phase 9, interval polling), đây là leak thật.

Cấu hình an toàn hơn: shareReplay({ bufferSize: 1, refCount: true }) — refCount: true khiến nó tự ngắt kết nối nguồn khi subscriber cuối cùng huỷ, rồi kết nối lại từ đầu nếu có subscriber mới.

💡 Khi nào DÙNG, khi nào KHÔNG cần shareReplay
Tình huốngCần shareReplay?
Chỉ 1 chỗ subscribe (ví dụ chỉ dùng | async MỘT lần trong template)Không — không có gì để "chia sẻ"
2+ chỗ subscribe CÙNG một Observable (template + TypeScript, hoặc 2 pipe async)Có — tránh gọi lại nguồn nhiều lần
Observable đã là state lâu dài qua BehaviorSubject (Bài 26 — auth state)Không cần — BehaviorSubject đã TỰ hot, tự chia sẻ giá trị cho mọi subscriber

🧠 Kiểm tra mental model

Câu 1. Template dùng {{ (data$ | async)?.x }} VÀ {{ (data$ | async)?.y }} — hai lần | async trên CÙNG một biến data$ chưa có shareReplay. Bao nhiêu HTTP request?
Câu 2. Vì sao BehaviorSubject (Bài 26 — auth state) KHÔNG cần shareReplay dù nhiều component cùng subscribe vào nó?

✅ Senior takeaway
  • Tôi chứng minh bằng thực nghiệm (không chỉ đọc doc) rằng cold Observable + nhiều subscribe = nhiều request thật.
  • Tôi biết dùng shareReplay ĐÚNG CHỖ — không rải nó khắp nơi "cho chắc", vì BehaviorSubject/stream chỉ-1-subscriber không cần.

5. Câu hỏi tư duy

Bạn vừa cắt được request THỪA bằng shareReplay. Nhưng có một loại lãng phí khác, không phải THỪA REQUEST mà là TẢI TRƯỚC những thứ CHƯA CẦN DÙNG NGAY — ví dụ: AdminCourseTableComponent (Bài 38-40) bị tải sẵn trong bundle CHÍNH dù 95% người dùng EduCommerce không phải admin, không bao giờ vào trang đó.
