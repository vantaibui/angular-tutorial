1. Generic component — kiểu rò vào template

TypeScript 
export class DynamicFormComponent<TModel = Record<string, unknown>> {
  @Input({ required: true }) schema: FormFieldSchema<TModel>[] = [];

  // field.name: keyof TModel có thể là string|number|symbol -> ép về string ở MỘT chỗ,
  // KHÔNG để template đọc field.name trực tiếp (lỗi biên dịch template).
  fieldName(field: FormFieldSchema<TModel>): string { return field.name as string; }
}
// Test component generic trực tiếp: PHẢI khai rõ tham số generic —
// truyền class như GIÁ TRỊ không tự áp dụng default type parameter.
TestBed.createComponent<DynamicFormComponent<Record<string, unknown>>>(DynamicFormComponent);
🔥 Interface cụ thể không tự khớp Record<string, unknown>

Course (interface, không index signature) KHÔNG được TypeScript coi là tương thích với Record<string, unknown> dù mọi field đều string-keyed hợp lệ — quirk kinh điển, không phải bug.

2. markForCheck() — không chỉ vẽ lại view của chính nó

🔥🔥 Phát hiện quan trọng: markForCheck() còn quyết định @Input có LAN TRUYỀN xuống con hay không

Thiếu markForCheck() ở cha: property cha ĐÚNG giá trị, nhưng ngOnChanges() của CON hoàn toàn không được gọi trong lần detectChanges() kế tiếp — dù binding [input] vẫn còn đó. Verify bằng probe tối giản (host+child thuần, không HTTP/RxJS).

Áp dụng cho MỌI nơi mutate field được bind xuống con từ callback ngoài event template (Bài 16 CVA → 29 CourseList → 31 CourseDetail → 37 event bus → 38 form cha/con — 5 lần liên tiếp, cùng 1 quy tắc).

3. CDK Table — cột định nghĩa riêng, hàng chỉ lắp ráp

HTML 
<table cdk-table [dataSource]="items" [trackBy]="trackByFn">
  <ng-container cdkColumnDef="title">
    <th cdk-header-cell *cdkHeaderCellDef>Tiêu đề</th>
    <td cdk-cell *cdkCellDef="let row">{{ row.title }}</td>
  </ng-container>
  <tr cdk-header-row *cdkHeaderRowDef="displayedColumns"></tr>
  <tr cdk-row *cdkRowDef="let row; columns: displayedColumns"></tr>
</table>

Đổi thứ tự/ẩn hiện cột chỉ cần đổi mảng displayedColumns — không sửa phần định nghĩa cột.

4. trackBy — chứng minh bằng đúng kịch bản

Kịch bản testCó cần trackBy để giữ DOM?
Sort lại MẢNG hiện có (object bên trong giữ nguyên tham chiếu)❌ Không — so khớp mặc định theo tham chiếu đã đủ
Gọi lại API, response JSON MỚI (object mới, cùng id)✅ Có — không có trackBy sẽ huỷ + tạo lại toàn bộ DOM row
🔥 Test sort-lại-mảng KHÔNG chứng minh được giá trị của trackBy

Phải test đúng kịch bản "server trả object mới cùng id" (vd sau khi xoá 1 dòng rồi load lại) mới thấy được sự khác biệt trackBy tạo ra.

5. OnPush — điều kiện an toàn

Trước khi bật OnPushKiểm tra
Mọi chỗ đổi mảng/objectGán REFERENCE MỚI (spread/map/filter), không .push()/mutate tại chỗ
Mọi .subscribe() thủ côngGọi markForCheck() sau khi mutate state

Code viết đúng kỷ luật zoneless (Bài 16 trở đi) đã tự động thoả điều kiện OnPush — bật cờ này thường không cần sửa logic.

6. Virtual scroll — giới thiệu, giới hạn test

HTML 
<cdk-virtual-scroll-viewport itemSize="48" style="height: 400px">
  <div *cdkVirtualFor="let item of items; trackBy: trackByFn">{{ item.title }}</div>
</cdk-virtual-scroll-viewport>
🔥 jsdom không tính layout — không đếm chính xác số DOM row được trong test

getBoundingClientRect() luôn trả 0 trong jsdom, kể cả sau khi ép qua viewport.checkViewportSize(). Test chỉ xác nhận cấu trúc CDK đúng + không throw với dữ liệu lớn; xác minh "chỉ render dòng nhìn thấy" bằng mắt trong trình duyệt thật.

7. Góc phỏng vấn

Câu hỏiTrả lời gọn
trackBy/OnPush/virtual scroll khác nhau ở đâu?trackBy giảm huỷ-tạo-lại DOM khi identity không đổi; OnPush giảm số component bị CHECK; virtual scroll giảm số DOM node tồn tại cùng lúc. Ba vấn đề độc lập, không thay thế nhau.
Điều kiện an toàn để bật OnPush?Mọi thay đổi state phải qua reference mới (không mutate tại chỗ), và mọi mutate ngoài event template phải gọi markForCheck().
Generic component có nhược điểm gì?Kiểu generic không ràng buộc (keyof TModel) có thể rò vào template gây lỗi biên dịch — cần ép kiểu tường minh qua method, không để rải rác trong template.
