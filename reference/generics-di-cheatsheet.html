A1. Cú pháp — bảng tra nhanh

DạngCú phápGhi chú

Interfaceinterface Res<T> { data: T }Khuôn cho mọi entity
Classclass Repo<T> { }Sau tên class; mọi member dùng chung T

Nhiều tham số<T, K extends keyof T>Mỗi cái giữ một mối liên hệ riêng
💡 Câu chốt

any nói "tôi không quan tâm kiểu gì". <T> nói "tôi chưa biết kiểu gì, nhưng đầu ra sẽ đúng bằng đầu vào". Generics giữ quan hệ giữa các vị trí trong chữ ký — thứ any xoá sạch.

A2. Constraint — cuộc trao đổi

TypeScript 
// ❌ T trần = "bất kỳ kiểu nào" → TS không cho giả định gì
function layId<T>(item: T) { return item.id; }
//                                        ^^ Property 'id' does not exist on type 'T'

// ✅ Ràng buộc thu hẹp tập kiểu, đổi lại mở quyền truy cập
function layId<T extends { id: string }>(item: T) { return item.id; }

Luật: ràng buộc vừa đủ để làm được việc, không hơn. Cần .id thì ràng buộc { id: string } — đừng viết T extends Course, vì thế là biến generic thành không-generic.

A3. keyof và vì sao cần hai tham số kiểu

TypeScript 
// ✅ K "ghim" đúng key được truyền → trả về ĐÚNG T[K]
function layTruong<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }

const t: string = layTruong(course, 'title');   // ✅ string
const p: number = layTruong(course, 'price');   // ✅ number

// ⚠️ Nếu viết (obj: T, key: keyof T): T[keyof T] thì kiểu trả về là UNION
//    của MỌI field → lại phải ép kiểu ở chỗ dùng.

A4. Utility types

Partial<T> lỏng ở chiều "được bỏ qua field" nhưng vẫn chặt ở chiều "tên field phải có thật và đúng kiểu".

A5. Khuôn InMemoryRepository<T>

TypeScript 
export class InMemoryRepository<T extends { id: string }> {
  private items: T[] = [];

  add(item: T): void { this.items.push(item); }

  // `| undefined` vì tìm không thấy là chuyện bình thường — kiểu phải nói THẬT
  findById(id: string): T | undefined { return this.items.find((x) => x.id === id); }

  update(id: string, patch: Partial<T>): void {
    const i = this.items.findIndex((x) => x.id === id);
    if (i === -1) return;
    this.items[i] = { ...this.items[i], ...patch };   // object MỚI → OnPush/NgRx phát hiện được
  }

  getAll(): readonly T[] { return this.items; }   // chặn push từ bên ngoài
}
Quyết địnhLý do
T | undefinedKiểu trả về phải nói thật, ép nơi gọi xử lý
{...cũ, ...patch}Object mới ⇒ so sánh tham chiếu phát hiện thay đổi (OnPush, NgRx)
readonly T[]Đóng cửa ghi bằng compiler, không bằng lời dặn

A6. Test tầng kiểu bằng @ts-expect-error

bash + TypeScript 
// Ý nghĩa: "dòng NGAY DƯỚI phải có lỗi biên dịch".
//   có lỗi   → build PASS
//   hết lỗi  → build FAIL: TS2578 Unused '@ts-expect-error' directive

// @ts-expect-error
layId({ name: 'không có id' });
bash · lệnh chấm bài 
npx tsc --noEmit -p tsconfig.spec.json   # im lặng = mọi ràng buộc kiểu còn hiệu lực
npm test                                 # runtime

Mạnh hơn @ts-ignore: @ts-ignore chỉ tắt tiếng, còn @ts-expect-error báo động khi lỗi biến mất — tức là nó bảo vệ ràng buộc kiểu của bạn khỏi bị vô hiệu hoá trong lần refactor sau.

⚠️ Generic bị XOÁ lúc runtime

Type erasure: file .js sinh ra không còn dấu vết <Course>. Nghĩa là http.get<Course>() không validate response — dữ liệu bẩn từ API vẫn lọt. Generic bảo vệ ở tầng biên dịch, không phải tầng runtime.

B1. Thứ tự resolve — "gần nhất thắng"

Thứ tự tìm kiếm 
Component xin CartService
   ├─ 1. ElementInjector của CHÍNH nó       ← @Component({ providers: [...] })
   ├─ 2. ElementInjector của component CHA
   ├─ 3. ... ngược lên gốc cây DOM
   ├─ 4. EnvironmentInjector của module     ← @NgModule({ providers: [...] })
   ├─ 5. ... ngược lên injector gốc         ← providedIn:'root' / @Service()
   └─ 6. NullInjectorError  (@Optional() → null)

// Dừng ở CÁI ĐẦU TIÊN tìm thấy.
Đặt ởSố instanceDùng cho
providedIn: 'root'1 cho toàn appAuth, Cart, Config, Logger. Tree-shakable.
@NgModule({providers})1 cho phạm vi injector đó⚠️ Module eager vẫn gộp vào gốc — vẫn là singleton toàn app
@Component({providers})1 cho mỗi instance componentState cục bộ: panel so sánh, form nháp, wizard step
🔥 Hiểu nhầm phổ biến nhất

"Đặt providers trong feature module thì service chỉ sống trong module đó" — SAI với module eager. Chỉ lazy-loaded module mới tạo EnvironmentInjector con thật sự.

B2. Bốn kiểu provider

TypeScript 
{ provide: APP_CONFIG,  useValue: { apiUrl: '/api' } }         // giá trị có sẵn

{ provide: LoggerAbstract, useExisting: ConsoleLogger }          // bí danh, cùng instance

B3. InjectionToken — inject thứ không phải class

TypeScript 
export interface AppConfig { apiUrl: string; pageSize: number; }

// interface BIẾN MẤT khi biên dịch → không có gì làm khoá DI.
// InjectionToken là object THẬT tồn tại runtime, mang kiểu ở tầng type.
export const APP_CONFIG = new InjectionToken<AppConfig>('app.config');

providers: [{ provide: APP_CONFIG, useValue: { apiUrl: '/api', pageSize: 20 } }]

private config = inject(APP_CONFIG);   // type-safe, IDE gợi ý .pageSize

B4. multi: true

TypeScript 
providers: [
  { provide: HTTP_INTERCEPTORS, useClass: AuthInterceptor,    multi: true },
  { provide: HTTP_INTERCEPTORS, useClass: LoggingInterceptor, multi: true },
]
// → inject(HTTP_INTERCEPTORS) trả MẢNG, chạy theo ĐÚNG thứ tự khai báo.
🔥 Quên multi: true

Provider sau ghi đè cái trước → mất một interceptor, không có lỗi nào. Triệu chứng: request đột nhiên không kèm token. Bạn sẽ đi tìm bug ở AuthService thay vì ở dòng provider.

B5. @Injectable vs @Service (Angular 22)

TypeScript · cả hai chạy song song, đã verify 
// CỔ ĐIỂN — mọi codebase v12–v16 dùng cái này
@Injectable({ providedIn: 'root' })   class A {}
@Injectable()                          class B {}   // phải tự khai providers

// MỚI ở Angular 22
@Service()                              class C {}   // ≈ providedIn:'root'
@Service({ autoProvided: false })       class D {}   // ≈ @Injectable() trần

@Injectable không bị deprecated (đã kiểm trong @angular/core@22.1.2). Khoá này dùng @Injectable có chủ đích vì mission là đọc hiểu codebase cũ — nhưng biết @Service() tồn tại để trả lời phỏng vấn cho chính xác.

B6. Test DI bằng TestBed

TypeScript 
TestBed.configureTestingModule({ imports: [DemoModule], providers: [GioHangService] });

const f1 = TestBed.createComponent(MyComponent);
const f2 = TestBed.createComponent(MyComponent);

// ⚠️ Dùng toBe (tham chiếu), KHÔNG dùng toEqual —
//    hai instance rỗng khác nhau vẫn toEqual nhau → test xanh vô nghĩa.
expect(f1.componentInstance.svc).toBe(f2.componentInstance.svc);       // dùng chung
expect(f1.componentInstance.svc).not.toBe(f2.componentInstance.svc);   // riêng biệt

Component dùng trong test phải có standalone: false, được declarations trong một @NgModule, rồi imports module đó vào TestBed. Gọi lại configureTestingModule ở mỗi test khi đổi providers.

B7. Góc phỏng vấn

Câu hỏiTrả lời gọn
T vs T extends {id: string}? T trần là "bất kỳ kiểu nào" nên TS chỉ cho làm những gì đúng với mọi kiểu — truy cập .id bị chặn. Ràng buộc thu hẹp tập kiểu hợp lệ, đổi lại mở quyền dùng .id. Là một cuộc trao đổi.
Generic class vs generic function? Class khi có state cần giữ đúng kiểu qua nhiều lời gọi (Repository<T> nhớ mảng nó giữ). Function khi chỉ biến đổi vào–ra.
Thứ tự resolve DI? ElementInjector của chính nó → các ElementInjector cha → EnvironmentInjector → gốc → NullInjectorError. Dừng ở cái đầu tiên gặp được.
Làm sao có instance service riêng cho mỗi component? Khai providers: [X] trong @Component — tạo ElementInjector riêng cho mỗi instance component.
multi: true để làm gì? Cho nhiều provider cùng token cộng dồn thành mảng thay vì ghi đè nhau. Cơ chế của HTTP_INTERCEPTORS, NG_VALIDATORS, NG_VALUE_ACCESSOR.
